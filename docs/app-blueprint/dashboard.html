What is Strummy?

Strummy is a student-management system for guitar teachers — a single-teacher CRM/LMS run by its owner for his own studio, live at strummy.vercel.app. The teacher schedules lessons, curates a song catalog, and assigns repertoire and homework; students log in to see their lessons, songs, and assignments, and log practice. Around that core sit an AI assistant (10 task agents over OpenRouter / local Ollama), a 17-type notification engine with Gmail SMTP delivery, two-way Google Calendar sync, Spotify enrichment, a chord quiz with SM-2 spaced repetition (teacher-assignable drills), a theory-course LMS, a parent family portal, and a video/social content pipeline. Stack: Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS 4 · Supabase (Postgres + Auth + RLS, self-hosted on home infrastructure).

Who uses it — roles

Teacher / Admin

Full CRUD on every domain. Schedules lessons, curates songs, assigns homework & chord drills, reviews practice and student health. Admin and teacher views coincide — the owner is the only teacher. AI tools, content pipeline, and observability are staff-only surfaces.

Student

Reads own lessons, songs, assignments; writes only where explicit: advance assignment status, log practice (immutable, same-day undo), self-rate repertoire, request songs. Isolation proven by cross-role RLS E2E. Shadow students — teacher-created profiles without accounts — are claimed later via invite.

Parent

Family-portal dashboard (shipped 2026-07-23): child check-in, practice activity, lessons, and teacher notes for the linked child, via parent-read RLS policies. Billing is stubbed (parked).
A trust pass, not a feature pass — onboard 5 real students onto an honest, narrow surface; everything else stays nav-hidden until real usage pulls it out. strategic frame · decided 2026-06-22 · reaffirmed 2026-07-18

Graduation rule

menuConfig.ts is a per-feature “reveal when proven” ledger. A student-facing feature leaves nav-hidden by attaching to the teacher-driven loop — assignable, with its outcome visible to the teacher — never by a blanket flip. Teacher/admin tools (content planner, analytics, Spotify, Drive) are a separate surface the student trust-pass never governed.

Mockup Represents Implementation Status E2E Unit

Every component in components/, grouped by domain. Every description ends with the same facts — which routes reach the component, the props it takes, how many sub-components it is split into. What differs is the opening sentence: derived means the file carries no doc comment of its own, so the sentence is composed from its name and position. Prop-level JSDoc is deliberately not treated as a component description. Reach is computed from a transitive import graph rooted at every app/ entrypoint — a component flagged unreached is imported by nothing a route can get to.

Testing comes from a real Jest run over components/** — not the repo's normal coverage config, which scopes to business logic and skips the component tree entirely. tested means a test file imports the component directly, and the number after it is how many do. indirect means no test names it, but it executes as part of somebody else's test, so a regression in it can still surface. untested means not one statement has ever run. The percentage is statement coverage. Mind the shape: coverage here is bimodal — 138 components sit at 100% and 97 at 0% — so the median flatters the tail. Filter by Never executed by a test for the real worklist.

Every page route the App Router serves, from app/**/page.tsx. Area is the URL segment the route sits under, not a security claim — access is enforced by RLS first and route guards second (see ARCHITECTURE.md).
