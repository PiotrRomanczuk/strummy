What this work is actually for, and what finishing it looks like

This session began as “test the invitee process on production.” That surfaced a class of bug rather than a single bug, so the work grew. This document states the goal plainly, shows exactly where things stand, and defines 100% as criteria you can check rather than a feeling.

The goal, in one sentence

Make Strummy's database schema, its TypeScript types, and its deployment pipeline agree with each other — so that a bug like the broken invite flow is caught by a machine before a user ever meets it, instead of being discovered by hand in production months later.

Everything below is in service of that. The invite bug was the symptom that made the underlying problem visible; fixing only the symptom would guarantee a repeat.

Why this grew beyond “fix the invite button”

The invite failure was not an isolated defect. The July 2026 identity rebuild dropped several database columns, but the checked-in TypeScript type files still declare them. That combination is uniquely nasty:

  • npm run typecheck passes, because the types claim the columns exist.
  • Postgres rejects the entire query with error 42703 when a select names a column that doesn't exist — so one dead column breaks a whole feature.
  • Nothing in CI runs those code paths against a real database, so it only ever fails in front of a user.

Searching for that pattern found four separate live bugs, only one of which had been reported. That is the evidence that the root problem is the drift itself, not any individual query.

Workstream B · roughly half done

Restore a real staging gate, so production stops being the test environment

The reason this bug survived so long is that there was nowhere to test. Feature branches produced no deployment at all, and merging to main deploys straight to strummy.online — Vercel's production branch is set to main, which contradicts the two-stage model described in CLAUDE.md.

Step Status
PR branches build a real preview again Done (#597)
Dev database reachable from Vercel (dev-only tunnel hostname) Done
Preview environment has its own Supabase credentials, pointed at dev Done
Bring production branch up to date with main Not started
Flip Vercel's production branch to production Blocked by the row above
Ordering matters here. The production branch is roughly 25 commits behind main. Flipping the Vercel setting first would make the next production deploy a rollback of today's entire batch of fixes. Sync first, flip second.
Workstream C · not started — this is the one that prevents recurrence

Make the drift impossible to reintroduce

There are four separate Database type definitions in the repo. None re-exports another. All four disagree with the database and with each other, and there is no script that generates any of them. Measured against the live profiles table alone:

File Columns declared Phantom
(declared, doesn't exist) 		Missing
(exists, invisible to TS)
database.types.ts 43 8 3
types/database.types.ts 24 3 17
types/database.types.generated.ts 31 6 13
types/supabase.ts 27 4 15

Every phantom column is a latent 42703 waiting for someone to select it. Until this is fixed, TypeScript actively provides false confidence — it will keep autocompleting columns that will crash at runtime.

What 100% means — concrete, checkable

Not “it feels finished.” These are things you or CI can verify. Ticked items are already true today.

A · Nothing currently broken by the drift

  • A teacher can invite a student and the invitee receives a working email — verified on production
  • Every code path that queried a dropped column has been found and fixed — audited across all 58 live tables
  • Both restored objects exist in production with correct RLS — verified by direct inspection
  • The full unit suite, typecheck and lint pass — 297 suites / 3,856 tests
  • A teacher can save per-song lesson notes in the UI (column is live; the click-path itself is unexercised)
  • The daily status cron writes audit rows and logs no errors (needs one overnight run to confirm)

B · A change can be tested before users see it

  • Opening a PR produces a working preview deployment backed by the dev database
  • production is up to date with main
  • Vercel's production branch is production; merging to main deploys to staging only
  • strummy.online changes only via a deliberate main → production release
  • CLAUDE.md matches what the pipeline actually does (today it does not)

C · This class of bug cannot come back

  • One generated file is the single source of truth for database types
  • A documented script regenerates it from the live schema
  • The other three type files are re-exports, not independent copies
  • Zero phantom columns remain in any type file
  • CI fails when the committed types drift from the schema
  • Schema parity between dev and production is green (currently 4 diff lines — see below)
Honest read on effort. A is essentially finished and is the part that was hurting users. B is small — one branch sync and one dropdown, with a sequencing trap. C is the largest and least glamorous, and it is the only one that stops this recurring. If only one thing gets done from here, it should be C.
