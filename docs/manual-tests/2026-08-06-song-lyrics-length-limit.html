Lyrics field length limit — raised, and surfaced before save

Date: 2026-08-06  ·  Branch: fix/song-lyrics-length-limit  ·  Reported: saving an imported Ultimate Guitar tab on production

The bug

Importing a full ASCII tab and pressing save failed with Too big: expected string to have <=20000 characters. The paste panel had already cleared itself by then, so the error arrived at the worst possible moment — after the content was committed to the form and the source was gone.

The 20,000 cap was an application-level bound in the two song server actions, not a storage one: songs.lyrics_with_chords is a text column with no length limit. It had never been hit before because it is comfortable for chord-over-lyric sheets — the longest lyrics in production is about 4,200 characters, and no row exceeded 20,000. A tab is a different shape of content: six string lines per system multiply the character count several times over, so the importer could produce something the form would not accept.

The fix

  • Limit raised to 100,000, defined once as LYRICS_MAX_LENGTH in schemas/CommonSchema.ts. That fits a full transcription while still bounding a runaway paste. Nothing downstream is length-sensitive: search_vector is generated from title and author only, so lyrics never reach a tsvector.
  • All four call sites now reference the constant — both server actions and both textareas' maxLength. They were four independent literals; a UI cap that disagrees with the schema is content that types fine and fails to save.
  • The importer warns before you apply. If a parsed tab still exceeds the limit, the "Found" preview says so in red. Apply is deliberately left enabled — the content is not silently discarded or truncated, you just know in advance that trimming is needed.

Edge cases worth a look

  • A song saved before this change still opens and saves normally — no data migration was needed
  • Typing (rather than pasting) into the lyrics box is no longer cut off at 20,000 characters
  • The detail page's rendering of a ~30,000-character tab stays responsive

End-to-end check

A synthetic ASCII tab of 27,008 characters — deliberately past the old 20,000 cap — was entered through the real create form and saved: 

textarea maxlength attr   100000        (was 20000)
characters entered         27,008
save                       succeeded, redirected to the song
DB after save              ZZ Long Tab Probe | 27,847 characters

The probe song was deleted from the dev database afterwards.

Note on where this was verified

Another Claude session was working in the main checkout at the time, so this was built and tested in an isolated git worktree. The repo's jest config ignores /worktrees/ (that guard prevents duplicate-haste-map collisions), so the suite was run with the ignore list restated minus the worktree entries — the same set npm test uses otherwise.
