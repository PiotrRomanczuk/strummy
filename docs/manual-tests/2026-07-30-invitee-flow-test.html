Strummy invitee flow test

Date: 2026-07-30  ·  Environments: strummy.online (production, where the bug was found) and a Vercel preview deployment wired to the StudentDevelopment stack (where the fix was verified)  ·  Method: live browser walkthrough, Vercel runtime logs, direct schema introspection, and an end-to-end invite send confirmed in the dev stack's mail catcher.

Correction to the first version of this report

The first version of this document (and PR #595) blamed row-level security for this bug. That diagnosis was wrong. It was written from a code read without any way to verify it, and the bug reproduced identically after that "fix" shipped. The real cause is a dropped database column, confirmed below by reading the actual Postgres error. The admin-client change from #595 is still correct and has been kept, but it was never the reason invites failed. This version supersedes the original.

Headline

Teachers could not invite a student at all — every "Invite to claim → Send" returned a server error and no email was ever sent. The cause was a query selecting profiles.sign_in_count, a column the July 2026 identity rebuild removed. Postgres rejects the whole query, so the lookup came back empty and the user was told "User not found". The same root cause silently broke three other features. Fixed in PR #598 and verified end-to-end on a preview deployment.

Step Result
Add a student (teacher side) Always worked
Invite to claim → Send 500, no email → Fixed & verified
Invite email actually generated Confirmed — "You've been invited to Strummy", correct recipient
Auth invite registered (invited_at set, unconfirmed) Confirmed
Clicking the claim link → student dashboard Not completed — see "Still open" below
Production data left behind None — every test profile deleted

Root cause

The sanitized production error (digest 3955190454) only said "User not found". Adding the discarded Supabase error to the log and reproducing on a preview gave the real one:

column profiles.sign_in_count does not exist (Postgres 42703)

Postgres rejects the entire query when the select list names a column that does not exist — so the profile lookup returned nothing and the code faithfully reported "User not found".

Verified directly against both databases: profiles.sign_in_count, profiles.last_sign_in_at, profiles.deletion_scheduled_for and the increment_sign_in_count() function are all absent. They were removed by the July 2026 identity rebuild and never carried into the rebuilt schema.

Why nothing caught it: the checked-in generated type files (database.types.ts, types/database.types.generated.ts, types/supabase.ts) still declare all of them. So npm run typecheck passes, the editor autocompletes the dead columns, and the failure only appears at runtime against a real database — which nothing in CI does for these paths.

Everything this broke

All four share the single root cause above. Only the first was reported; the rest were found by grepping for the dead columns.

Feature Symptom Scope
Invite a student to claim their account Server error, no email Every unclaimed student, every teacher
View your profile (GET /api/users/profile) "Profile not found" (404) Every user
Save your profile (PATCH /api/users/profile) "Failed to update profile" (500) Every user
Request / cancel account deletion Silently failed Every user
Sign-in tracking Called a function that no longer exists, on every login Every sign-in (invisible)

Two latent id-space bugs found alongside, both fixed: the invite flow and the account-deletion flow passed an app profile id where an auth account id was expected. Since the rebuild those are independent id spaces, so both would have addressed the wrong account — the same class of bug as PRs #588–#591.

How the fix was verified

This is the part the first report could not do — there was no environment to test in. There is now: PR previews build again, and Preview is wired to the dev stack rather than production.

  1. Signed in to the preview deployment as the dev teacher account (proves Preview reaches the dev database at all).
  2. Added a student, clicked Invite to claim → Send.
  3. POST /dashboard/users/<id> returned 200 (was 500), and the button changed to ✓ Invite sent.
  4. Confirmed in the auth admin API that the invitee now exists with invited_at set, confirmed_at null, last_sign_in_at null — exactly an outstanding invite.
  5. Read the actual email out of the dev stack's mail catcher: subject "You've been invited to Strummy", correct recipient, containing a well-formed type=invite verification link.
  6. Full unit suite green (297 suites / 3856 tests), typecheck and lint clean.

Still open

  • Clicking the claim link end-to-end was not completed. On the dev stack the invite link's redirect_to falls back to that stack's own SITE_URL (127.0.0.1:3000) because the preview URL is not in its redirect allow-list — so the link cannot be followed from outside the LAN. The link itself is correctly formed. Worth explicitly checking on production that APP_URL//accept-invitation is allow-listed in the production Supabase project, otherwise real invitees could land on the wrong page.
  • The generated type files are stale. Until they are regenerated from the live schema, TypeScript will keep failing to catch this entire class of bug, and the dead columns will keep autocompleting. Worth doing deliberately as its own change, plus a CI drift check.
  • A uq_profiles_invite_email unique constraint means one invite email address cannot be reused across two profiles — hit while testing. Harmless here, but it will surface as a confusing error if a teacher ever re-uses an address.
  • One test student (Invite Fix Verified) remains on the dev stack. Nothing was left on production.

Infrastructure changed to make this testable

Verifying this bug required an environment that did not exist. Three changes, all reversible:

  • PR previews build again (#597) — vercel.json previously built only main and production. Now any branch with an open PR builds too. Caveat: the branch must be pushed after the PR is open, or the build is skipped (the PR id is what the condition tests).
  • The dev database is reachable from Vercel — added a dev-only hostname to the existing Cloudflare tunnel on uwh, alongside the long-standing production one. Same exposure model, still key-gated.
  • Preview has its own Supabase credentials, pointed at the dev stack. Previously Preview had none at all, so any preview would have failed on every database page.

Also worth knowing: merging to main deploys straight to strummy.online — the main deployment carries the production domain alias. The "main = staging" split described in CLAUDE.md is not what Vercel is actually doing.

How to re-test this yourself

  1. Sign in as a teacher. Go to Students → + New student.
  2. Enter a name and a student email you control, then Add student.
  3. On the new student's page click Invite to claim, confirm the address, Send.
  4. Expected: the button becomes "✓ Invite sent" with no error, and the invite email arrives at that address.
  5. Also worth a click while you're there: open Settings → Profile and save a change — that path returned "Profile not found" for everyone before this fix.
