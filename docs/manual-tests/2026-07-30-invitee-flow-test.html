Bug found

High — teacher-facing, fully broken, zero invites can be sent

"Invite to claim" (and "Reach out" → Send) throws a 500 for every unclaimed student

Steps to reproduce: sign in as a teacher → Dashboard → Invite student (or Students → + New student) → fill in Full name + Student email → Add student → on the new student's detail page, click Invite to claim → confirm the email in the inline field → Send.

Observed in the browser (rendered directly in the page, replacing the invite form):

An error occurred in the Server Components render. The specific message is omitted in production builds to avoid leaking sensitive details. A digest property is included on this error instance which may provide additional details about the nature of the error.

Network tab confirmed the underlying request: POST /dashboard/users/<id> → 500. Vercel runtime logs resolved the sanitized digest (3955190454) to the actual server-side exception:

Error: User not found at g (.next/server/chunks/ssr/_1b81fsr._.js:2:5625) { digest: '3955190454' }

Root cause (confirmed, not just "likely"): sendUserInvite() in app/dashboard/actions.ts re-reads the target profile with the RLS-scoped supabase client:

- const { data: targetProfile } = await supabase .from('profiles') .select('email, is_shadow, invite_email, sign_in_count, full_name') .eq('id', userId) .single();

The profiles RLS SELECT policy does not grant a teacher read access to an unclaimed ("shadow") student's row — only the preceding UPDATE in inviteShadowUser() (which persists the real e-mail into invite_email) is permitted. So this SELECT always resolved to null, and the very next line — if (!targetProfile) throw new Error('User not found') — fired on every single invite-to-claim attempt in production. This is the same class of bug as the AI Chat RLS issue fixed same-day in PR #594: a server action reads through the caller's RLS-scoped client for a row the caller isn't allowed to SELECT, even though it's allowed to act on it in a more limited way.

Fix applied (this session, not yet merged): read the target profile with the already -created supabaseAdmin client instead, since the caller's admin/teacher role was already verified a few lines above via the RLS client:

const supabaseAdmin = createAdminClient(); const { data: targetProfile } = await supabaseAdmin .from('profiles') .select('email, is_shadow, invite_email, sign_in_count, full_name') .eq('id', userId) .single();

Added 5 regression tests to app/actions/__tests__/dashboard-actions.test.ts covering: the admin-client read succeeding for a shadow profile, the "User not found" path when the admin lookup itself finds nothing, inviteShadowUser's persist-then-send happy path, the persist-failure path, and the student-cannot-invite authorization guard. npm run typecheck and npx eslint app/dashboard/actions.ts app/actions/__tests__/dashboard-actions.test.ts are both clean; the full test file (20/20) passes.
