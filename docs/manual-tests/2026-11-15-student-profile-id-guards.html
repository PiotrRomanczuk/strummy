Profile id, not auth id, in student and teacher guards (#1079)

Date: 2026-11-15 · Scope: assignment status + checklist actions, notification preferences, lesson-create API

What was done

A student invited after their first lesson claims a shadow profile: the account keeps the shadow's profiles.id, which differs from the auth id. Several guards compared a profile-id column with the auth id, so such a student could not start or complete an assignment, tick its checklist, or change notification preferences (the list loaded empty). The same comparison refused a teacher with a claimed profile their own lessons in POST /api/lessons, /api/teacher/lessons and /api/admin/lessons.

  • app/actions/assignment-status.ts, assignment-checklist.ts: ownership checked against profileId.
  • app/actions/notification-preferences.ts: authorised and filtered by the caller's profileId; the page and component pass profileId.
  • app/api/lessons/handlers/create.ts: takes the caller's profile id; all three routes pass it.
  • Deleted, per structure rule S5 (unmounted code is deleted, not maintained): app/actions/assignments.ts (updateAssignmentStatus, no caller) and app/actions/self-rating.ts + SelfRatingSchema (no UI calls it — students cannot self-rate a song today; mounting it is a feature, not this fix).
  • Tests now use accounts whose auth id ≠ profile id. Against the old code 25 of them fail; against the new code all pass.

Added 2026-11-16 — found by the first E2E run on StrummyTest

The copy of production has accounts like real invited users (profiles.id ≠ auth id); dev's role accounts have them equal, which is why the dev suite never saw this. The first run on StrummyTest (PR #1104) failed the five specs this PR already fixes, and exposed more places with the same mistake:

  • Calendar conflicts (fetchPendingConflicts): filtered lesson.teacher_id by the auth id — such a teacher always saw an empty list. calendar-conflicts.spec.ts A8.2 failed on StrummyTest.
  • Teacher dashboard (getTeacherDashboardData): students (teacher_students) and songs (lessons.teacher_id) by the auth id — no students, no songs.
  • Quick assign / repertoire (assignSongToStudentsAction, addSongToRepertoireAction): wrote assigned_by = auth id into a column referencing profiles — 23503 on every assign by such a teacher. Same in the three Spotify review routes (reviewed_by). song-detail-quick-assign.spec.ts passes on StrummyTest with the fix.
  • Student export (/api/exports/student/[id]): a teacher's allowed students and a student's "is this me" by the auth id — 403 on their own data.

Checked: with this PR applied, the five specs pass on StrummyTest. Unit tests now use an auth id different from the profile id: calendar-conflicts.test.ts, teacher-dashboard.test.ts (new case), exports/student/route.unit.test.ts. Manually (StrummyTest or any account whose profile id ≠ auth id): sign in as such a teacher → the dashboard lists their students; /dashboard/calendar/conflicts lists a seeded pending conflict; GET /api/exports/student/<student profile id> → 200.
