Repertoire gets filters; every list bar gets the same ones

2026-07-31 · branch feature/standardize-table-filters

What was actually done

Repertoire had no filtering at all. It now has stage chips (with counts), sort chips, and a title/artist search — the same controls, in the same order, with the same styling as the Song Library.

The four list pages previously had three different filter mechanisms: Songs and Lessons rendered chips as links; Assignments and Users pushed through the client router. Same interaction, different behaviour and slightly different look depending on which list you were on. They now share one primitive.

Before / after

Page Was Now
Repertoire No filters Stage chips + counts, sort chips, search
Songs Own chip style, own label style, own href builder Shared chip row; unchanged behaviour
Lessons Own chip style + a sort toggle (one link whose label flipped) Shared chip row; sort is two chips, so the current order is visible rather than inferred
Assignments Own tab component, bare controls with no container Shared chip row + the same bordered controls surface as the others

The shared pieces

  • components/shared/ListFilters.tsx — FilterBar, FilterRow, FilterChipRow, FilterControlsRow, and the shared control/label styles.
  • components/shared/ListFilters.Form.tsx — the text/select half. Selects apply immediately; text debounces at 350ms and uses replace so typing does not stack one history entry per keystroke. That came from Songs, the only page that had it right, and is now the behaviour everywhere.
  • components/shared/list-filters.helpers.ts — one href builder. "Changing a filter resets pagination to page 1" was previously re-decided (or forgotten) per page.

Chips are links, not router pushes, uniformly. They are navigations: they work without JS, they survive a reload, and a filtered view is shareable as a URL. Only the live-updating text/select controls ship client JS.

Decisions worth knowing

Repertoire filters in the app, not the database. The page already loads the student's whole repertoire in one RLS-scoped read and does not paginate, and a repertoire is tens of rows. If it ever paginates, this moves into the query — the logic is isolated in repertoire-filters.helpers.ts for exactly that reason.

Stage counts ignore the selected stage but respect the search. If counts narrowed to the selection, picking a stage would zero every other chip and strand you there with no way back except the URL. Clicking the active chip also clears it.

Never-practised songs sort last under "Recently practised." A null date treated as 0 would put them at the top, which is the opposite of what the sort says.

Two test-selector collisions, both real signals. Adding counts made a chip's accessible name read "Mastered3" — Playwright matches role names by substring, so it collided with a difficulty button lookup of '3'. The chip now renders an explicit space ("Mastered 3"), which also just reads better aloud. Separately, "Stage" now appears three times on Repertoire (filter label, sort chip, column header), so the header assertion is scoped to the header strip.

How to test it manually

cd ~/Desktop/MainCV/strummy
git checkout feature/standardize-table-filters
npm run dev

Sign in as the Student dev account (credentials in CLAUDE.local.md).

1 — Repertoire filters

  1. Go to My Repertoire. expect a STAGE chip row with per-stage counts, three sort chips right-aligned, and a search box below.
  2. Click a stage chip. The table narrows, the subtitle changes to "N of M songs", and the URL gains ?stage=….
  3. Reload. The filter must survive — these are links, not client state.
  4. Click the same chip again — it clears, and the URL returns to a bare path.
  5. Check the other chips still show their real counts while one is selected (they should not all read 0).
  6. Type an artist name (e.g. "beatles") in the search — matching by artist as well as title is the point. Counts narrow with the search.
  7. Search for nonsense — expect "No songs match these filters", not the generic empty-repertoire copy.
  8. Try each sort. Recently practised: never-practised songs at the bottom. Title: A→Z. Stage: mastered first.
  9. Combine a stage chip with a search, then paste the URL into a new tab — it should reproduce exactly.

2 — The other three still work

  1. Songs: level chips with counts, sort chips, and the key/author/search row. Behaviour should be unchanged.
  2. Lessons: status chips keep their coloured dots. Sort is now two chips — confirm the active one is filled dark and that clicking the inactive one switches order.
  3. Assignments: status chips with counts, and the search/sort controls now sit in the same bordered surface as the other pages. Check the sort dropdown and the asc/desc button still work together.
  4. Flip between all four pages — the bars should read as one system.

3 — Edge cases

  • Bad URL: /dashboard/repertoire?stage=nonsense should show the unfiltered list, not an empty table. An unrecognised stage is dropped rather than passed through.
  • Mobile: chip rows wrap rather than overflow; the search box goes full width.
  • Keyboard: tab to a chip and press Enter — it navigates. Chips carry aria-pressed so the active filter is announced.
  • Empty repertoire: chips all read 0 and the empty-state copy shows.

Follow-up

Assignments still owns its param logic. Its sort is paired with a direction param, which the generic form does not express; forcing it through would have either lost behaviour or bloated the primitive. Its presentation is standardized; its query handling is not.

Only Repertoire is on the DataList table primitive. Songs, Lessons and Assignments now share the filter bar but still have their own row/table code. That is the remaining half of the consolidation.

UsersList.FiltersForm (teacher-facing) was not migrated — it is not one of the four list pages in scope here.
