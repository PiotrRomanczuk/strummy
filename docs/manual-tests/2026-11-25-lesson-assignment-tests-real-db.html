What the real database showed

  • Another student or teacher gets "Assignment not found", not "You cannot change this assignment": RLS hides the row before app code sees it. The mock had returned the row.
  • A parent does read the child's assignment, so the app check "You cannot change this assignment" is reachable only for them.
  • The completion mail really is sent (to Mailpit): subject "Assignment Completed: RLS ćwiczenie" arrived for the fixture teacher.
  • Finding, not changed here: lib/services/calendar-lesson-sync.ts looks up user_integrations.user_id (an auth id) with lesson.teacher_id (a profile id). Since S2 these differ for new accounts, so Google Calendar sync silently never runs for them.

How to test manually

  1. On the LAN, with .env.local pointing at the dev stack: 
    npx jest -c jest.config.rls.ts app/actions/__tests__/lesson-edit.rls.test.ts app/actions/__tests__/assignment-status.rls.test.ts
    Expected: 2 suites, 31 tests passed.
  2. Mutation: remove 'status', from ALLOWED_UPDATE_FIELDS in app/actions/lesson-edit.ts and rerun. Expected: the two "saves status … (#873)" tests fail. Revert.
  3. Mail: open http://192.168.1.75:55324 (dev Mailpit). After the run there is an "Assignment Completed: RLS ćwiczenie" message to an rls-teacher-a-…@guitarcrm.local address, and nothing reached a real mailbox.
  4. Coverage locks: RLS_REQUIRED=1 npm run test:rls -- --coverage passes. Running one suite with --coverage fails the locks of the files it does not touch, which is expected and shows the locks are enforced.

Limits

  • Not covered on the real database: a database error without a message (fallback text) and a failed status write when the database is down. These are infrastructure failures, and the locks are set below 100% for them, as stated in jest.config.rls.ts.
  • Like #1195, these suites run only where the dev DB is reachable (Mac on LAN/Tailscale, self-hosted rls job).
