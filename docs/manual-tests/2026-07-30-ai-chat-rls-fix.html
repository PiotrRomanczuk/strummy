AI Chat no longer fails with a row-level security error

2026-07-30 · branch fix/ai-conversations-profile-id-rls · app/actions/ai-conversations.ts

What was wrong

Sending any message in AI Chat failed immediately. The chat bubble rendered a raw Postgres error instead of a response: 

new row violates row-level security policy for table "ai_conversations"

Found live on production while manually checking the +testteacher account (see 2026-07-30-production-feature-check.html), but the bug is in application code, not data — it affects every teacher account, real or test.

The cause is an id mix-up. ai_conversations.user_id is a foreign key to profiles.id (a separate generated PK — not the same UUID as auth.users.id), and its RLS insert policy checks the inserted row against current_profile_id(), which resolves profiles.id. But createConversation() was inserting user_id: userId where userId came from supabase.auth.getUser().data.user.id — the auth id, not the profile id. Those two ids are never the same, so the WITH CHECK clause failed on every single insert, for every account.

Why this specific mistake: the codebase's own getUserWithRolesSSR() helper has a comment warning about exactly this — "a caller that filters a profile-id column by an auth id gets zero rows rather than the wrong rows" — and app/actions/practice.ts already documents the same gotcha inline for practice_sessions.student_id. This file just didn't get the memo: it rolled its own getAuthUserId() helper returning the auth id instead of reusing profileId from getUserWithRolesSSR().

trackAIUsage() had the identical bug against ai_usage_stats.user_id (same profiles.id FK, same RLS shape) — it just failed more quietly, since its errors are swallowed and it's fire-and-forget usage tracking, not a user-facing action.

What changed

Both functions now destructure profileId from the getUserWithRolesSSR() call they already made (for the test-account guard), instead of a separate getAuthUserId() call, and use it as user_id:

  • createConversation() — inserts user_id: profileId; returns Unauthorized up front if profileId is empty (no profile row).
  • trackAIUsage() — both the existing-row lookup (.eq('user_id', profileId)) and the insert now use profileId; returns early (silently, matching its existing fire-and-forget error handling) if there's no profile.

saveConversationMessages() needed no change — ai_messages has no user_id column of its own; its RLS policy walks up to the parent conversation's user_id, which is now correct once conversations are created correctly. The five read/update/delete-by-id functions (listConversations, getConversation, updateConversationTitle, archiveConversation, deleteConversation) were never part of the bug — they never set user_id explicitly, and RLS's own USING clause already scopes them correctly. They're untouched, still using getAuthUserId() purely as an "is anyone signed in" check.

Verified

Check Before After
Unit tests — app/actions/__tests__/ai-conversations.test.ts 19/19 passed, but asserted nothing about which id was used 19/19 passed; 3 new regression-guard assertions now fail if the code ever reverts to the auth id
npm run typecheck — clean
npx eslint on both changed files — 0 errors (1 pre-existing max-lines warning, unrelated to this change)

The new tests use two deliberately different mock ids (MOCK_USER_ID vs. MOCK_PROFILE_ID) and assert the Supabase .insert()/.eq() calls were made with MOCK_PROFILE_ID — so a future regression back to the auth id fails loudly in CI instead of only surfacing as a live RLS error.

How to test it yourself

1. Automated (fastest)

npx jest app/actions/__tests__/ai-conversations.test.ts

Expected: 19 passed, including the 3 new regression guards.

2. By hand, once deployed

  1. Sign in as any teacher account (a fresh/role-less one is the strongest test — that's exactly what reproduced the bug).
  2. Open AI Chat in the sidebar.
  3. Send any message, e.g. "Suggest a beginner song in the key of G."
  4. Expected: a real streamed response from the assistant. Previously: the message failed instantly with new row violates row-level security policy for table "ai_conversations".
  5. Refresh the page — the conversation should now appear in the conversation history list (proof the row actually persisted, not just that the error went away).
Not yet verified against a live database — this was fixed and unit-tested from a read of the schema/RLS policies and the codebase's own established pattern for this exact class of bug (practice.ts's student_id fix). Recommend a live check on staging before promoting to production.
