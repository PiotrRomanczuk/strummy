Malformed ids returned 500 and leaked Postgres text

Date: 2026-07-27 · Branch: fix/api-uuid-validation · Found by: the local E2E run against the dev stack

A real bug, surfaced by the local E2E run against the dev stack. The sidebar failures from that same run turned out to be the opposite kind of problem — stale assertions against a correct app — and are handled separately in 2026-07-27-sidebar-spec-derives-from-config.html.

What was wrong

integration/workflows failed with expect(500).toBeLessThan(400). Reproduced directly against the running app: 

DELETE /api/song?id=songs      → 500  {"error":"invalid input syntax for type uuid: \"songs\""}
DELETE /api/song?id=not-a-uuid → 500  {"error":"invalid input syntax for type uuid: \"not-a-uuid\""}
GET    /api/lessons/not-a-uuid → 500  {"error":"invalid input syntax for type uuid: \"not-a-uuid\""}

A client-supplied id that isn't a uuid went straight into the query. Postgres raised 22P02, and the route returned it as a 500 carrying the raw driver message. Two defects in one: the wrong error class (a bad id is the caller's mistake, not the server's), and a needless leak of schema internals to the client.

The fix

A guard at the boundary — lib/api/validate-id.ts. It returns a discriminated result so the happy path also narrows string | null to string: 

const parsed = parseId(songId, 'Song');
if (!parsed.ok) return parsed.response;
// parsed.id is a validated uuid

Applied to PUT/DELETE /api/song and all three methods of /api/lessons/[id]. Separately, the two sites that returned error.message now go through the existing mapSupabaseError() — a helper already in lib/api/errors.ts whose own comment says "Don't leak raw DB messages to clients". The codebase already had the right tool; these routes just weren't using it.

Request Before After
DELETE /api/song?id=songs 500 + raw PG text 400 {"error":"Invalid song ID"}
DELETE /api/song?id=not-a-uuid 500 + raw PG text 400 {"error":"Invalid song ID"}
DELETE /api/song?id=<valid uuid> 400 not found 400 not found (unchanged)
DELETE /api/song?id= 400 required 400 required (unchanged)
GET /api/lessons/not-a-uuid 500 + raw PG text 400 {"error":"Invalid lesson ID"}
GET /api/lessons/<valid uuid> 404 404 (unchanged)

The test was also wrong

Fixing the 500 turned the E2E failure into expect(400).toBeLessThan(400) — because the spec derived the song id with page.url().split('/').pop(), and creating a song redirects to the list, so that expression returned the literal string "songs". The delete had never targeted the created row; the old 500 was masking it. It now looks the id up by title.

Scope note. The raw-message leak is not limited to these two routes — grep finds the same { error: error.message } shape in ~10 more (spotify/*, admin/drive-videos, content/*, repertoire/bulk, lessons collection and lessons/search). Deliberately left alone here so this change stays reviewable. Worth a follow-up sweep.

How to verify

1. The 500 is gone (the main check)

Start the app against the dev stack, get an admin token, and hit the endpoint:

npm run build && npx next start -p 3100

ANON=$(grep '^NEXT_PUBLIC_SUPABASE_LOCAL_ANON_KEY=' .env.local | cut -d'"' -f2)
TOKEN=$(curl -s "http://192.168.1.75:55321/auth/v1/token?grant_type=password" \
  -H "apikey: $ANON" -H "Content-Type: application/json" \
  -d '{"email":"admin@dev.local","password":"test123_admin"}' | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")

curl -i -X DELETE "http://localhost:3100/api/song?id=not-a-uuid" -H "Authorization: Bearer $TOKEN"

Expect 400 and {"error":"Invalid song ID"}. Critically, the response must not contain the words uuid, syntax, or any Postgres text.

2. The happy path still works

npx playwright test tests/e2e/integration/workflows.spec.ts \
  --config=playwright.local-3100.config.ts --project="Desktop Chrome" -g "song lifecycle"

Expect 1 passed — it creates a song, finds it in the list, and deletes it for real.

Test changes worth knowing about

  • Two tests asserted the leak and now assert the opposite: expect(result.error).toBe('Database connection failed') became toBe('An unexpected error occurred') plus an explicit not.toContain on the driver text.
  • New: four cases proving a malformed id is rejected at the boundary — including that maybeSingle() is never called, i.e. the database is not consulted at all.
  • app/api/song/handlers.ts gained 3 lines (264 → 267), so it still trips the max-lines warning at 200. That warning is pre-existing on main, not introduced here.
