Make main green again

Date: 2026-07-27 · Branch: fix/coverage-thresholds · Scope: test-only, no production code changed

Main was red for two independent reasons, in two different CI steps. Both are fixed here, because either one alone still leaves the pipeline failing.
① Unit tests step — four per-file coverage thresholds.
② Integration tests step — 8 failing AI-logging tests from a drifted mock (see §2). This one was pre-existing on main and unrelated to the coverage work; it was found only because CI runs an integration step that npm test does not.

① What was actually done — coverage thresholds

CI on main was failing even though every test passed. The cause was four per-file coverage gates in jest.config.ts that demand 100% on files whose newest functions had shipped without tests. Jest reports this as an exit-1 after printing "all suites passed", which is why it read as a mystery failure.

This change adds the missing tests. No application code was touched — behaviour is identical before and after; only __tests__ files changed.

Two mock-harness changes worth knowing about

Both existing test files mock the Supabase query builder by hand, and the newly-covered functions use chain shapes the old mocks did not model:

  • lessons-queries.test.ts — getLessonsBreakdown awaits the builder itself rather than a terminal like .limit()/.range(). The mock chain is now a thenable (as the real PostgREST builder is), resolving from a new mockAwaited fn.
  • assignment-templates.test.ts — saveAssignmentAsTemplate chains .select('id').single() off the insert, while createAssignmentTemplate awaits the insert directly. insert() now returns a value satisfying both shapes, and the read chain gained .is('deleted_at', null).

These are additive — every pre-existing test still passes unchanged, which is the check that the harness edits did not quietly alter what the old tests assert.

② Drifted mock in the integration suite

CI's Integration tests step was failing separately, with 8 tests down in app/actions/__tests__/ai-generation-logging.integration.test.ts — every streaming path erroring with: 

Error: (0 , _modelmappings.resolveOpenRouterModel) is not a function

The suite's jest.mock('@/lib/ai/model-mappings', …) factory returned only mapToOllamaModel. A jest module factory replaces the module wholesale, so once app/actions/ai/shared.ts started calling resolveOpenRouterModel as well, that import resolved to undefined in this suite. The two sibling suites (ai.test.ts, ai-streams.test.ts) had already been updated; this one was missed.

Fixed by adding the same stub they use, mirroring the real helper's behaviour (strip the retired :free suffix). Pre-existing on main — verified by running the suite on an unmodified checkout of main, where the same 8 fail.

How to manually verify

No UI to click through — this is a CI-gate fix. Verification is reproducing both gates.

1. Confirm both gates now pass (the main check)

CI runs two Jest steps. npm test alone only covers the first — which is exactly how issue ② stayed hidden. Run both: 

cd strummy
npm test;             echo "unit exit=$?"          # expect 0
npm run test:integration; echo "integration exit=$?"  # expect 0

For the unit run, expect no lines reading Jest: "./path" coverage threshold for … not met. Check the exit code explicitly, since Jest prints the pass summary either way. Expected totals: 279 suites / 3,689 passing (unit) and 15 suites / 205 passing (integration).

2. Confirm the three files are actually at 100%

npx jest \
  app/actions/__tests__/assignment-templates.test.ts \
  lib/services/__tests__/lessons-queries.test.ts \
  lib/services/__tests__/student-detail-queries.test.ts \
  --coverage \
  --collectCoverageFrom='app/actions/assignment-templates.ts' \
  --collectCoverageFrom='lib/services/lessons-queries.ts' \
  --collectCoverageFrom='lib/services/student-detail-queries.ts' \
  --coverageReporters=text --coverageThreshold='{}'

Expect 100 in all four columns for all three files, and an empty "Uncovered Line #s".

3. Confirm nothing else regressed

npm run lint
npx tsc --noEmit

Both should produce no output.

4. Prove the tests are real (worth doing once)

A coverage-driven test can pass vacuously. To confirm these actually assert behaviour, break the source on purpose and watch them fail — then revert:

  • In lessons-queries.ts, change if (!key) continue; to if (false) continue; → the "skips rows whose status is null or empty" test should fail.
  • In assignment-templates.ts, drop the done: false from the checklist map → the "resets checked items" test should fail.
  • In student-detail-queries.ts, change skillLevel ?? '' to skillLevel → the new empty-skill-level test should fail.

Edge cases covered

  • Authorization — student rejected, teacher-with-no-user rejected, admin allowed.
  • Template copy semantics — a checked checklist item is reset to done: false (a template seeds future work rather than mirroring past progress); ownership is forced onto the current user rather than trusted from the source row.
  • Malformed input — a non-array checklist on the source assignment degrades to [] instead of throwing; a missing description becomes null.
  • Failure paths — read error, missing row with no error, insert error, and insert returning no row all throw and skip revalidatePath.
  • Viewer scoping — breakdown scopes teachers to teacher_id, students to student_id, and admins to nothing at all.
  • Counting — statuses counted case-insensitively; unlabelled rows omitted from the chips but still counted in the total; query errors degrade to an empty breakdown plus a warn.
