Manual test: expandable row on the Songs list

Date: 2026-08-06

What was done

Songs list rows (components/songs/SongsList.Row.tsx) only showed title, author, level, and key. Rows already navigate to the full song detail page on click, so instead of a competing "click for details" dialog, a small chevron toggle was added to each row: clicking it expands a panel inline showing capo, tempo, time signature, duration, category, and strumming pattern — without navigating away. Clicking the row title/body still navigates to /dashboard/songs/[id] exactly as before.

SongRow became a Client Component (it needed local expand/collapse state); translations moved from a prop-drilled function to useTranslations('Songs') called inside the component, since Client Components can't receive functions as props. The detail panel itself lives in a new sibling file, SongsList.Row.Detail.tsx, kept separate to stay under this repo's per-function line-count convention.

How to manually test it

  1. Run npm run dev, sign in, and visit /dashboard/songs.
  2. Rows with any of category/capo/tempo/time-signature/duration/strumming-pattern set show a small chevron before the title. Rows with none of those set show no chevron (nothing to expand).
  3. Click the chevron — a panel appears below the row with the available fields, styled the same as the song detail page's hero meta row. Click again to collapse.
  4. Click the row's title/body (not the chevron) — navigates to the song's full detail page, unchanged from before this change.
  5. Check on a narrow (mobile) viewport — the chevron and panel still work; the row still collapses to its single-column mobile layout.

Pre-existing issue found (not caused by this change)

While testing, dashboard pages were found to double-render their entire content server-side — e.g. /dashboard/songs renders two <h1>Songs</h1> elements and two full copies of the page tree in the raw HTML response. Verified this happens identically on unmodified main (stashed this feature's changes and reloaded), so it predates and is unrelated to this work. It didn't visually double-render (only one copy is visible on screen — the second appears to have zero layout impact), but it did make one E2E assertion (click-and-wait-for-navigation) unreliable, worked around by asserting the link's href directly instead of clicking through. Worth a dedicated investigation separately — not fixed here as it's out of scope for this feature.
