Sentry client-side error reporting was silently disabled

Date: 2026-07-30  ·  Branch: fix/sentry-client-instrumentation  ·  Scope: browser-side Sentry init, Next 16 / Turbopack file convention

What was actually done

PR #570 turned Sentry back on and the server half worked, so the setup looked healthy. It wasn't. Not a single browser-side error was being reported — every error boundary, session replay, and breadcrumb went nowhere, while server errors flowed normally and masked the gap.

The cause is a file-name convention, not a logic bug. This project builds with Turbopack (Next 16's default; next.config.ts also enables turbopackFileSystemCacheForBuild). The Sentry SDK's Turbopack path bundles the client config by matching **/instrumentation-client.* and nothing else. The legacy name sentry.client.config.ts is read only by the SDK's webpack path, which never runs here. So the file type-checked, linted, imported cleanly, read as correct in review — and was never bundled. Sentry.init never executed in a browser.

The change is deliberately small:

  • sentry.client.config.ts → instrumentation-client.ts (a pure rename; file contents were already correct, including the onRouterTransitionStart export that had been inert).
  • A ratchet test at __tests__/architecture/sentry-client-instrumentation.test.ts that fails if the legacy name ever returns. This failure mode is invisible to builds, types, and lint, so a static guard is the only thing that catches it.
  • Stale comment references in sentry.server.config.ts, sentry.edge.config.ts, and .github/instructions/error-handling-logging.instructions.md updated to the new name, with a note about why the old one is a trap.
  • CLAUDE.md deployment section corrected — see the warning below.
Discovered while verifying, unrelated to the rename: main deploys straight to production. The live deployment carries the strummy-git-main-… alias and there is no production branch in the repo. Separately, vercel.json's ignoreCommand cancels every non-production build after a few seconds, so strummy-preview.vercel.app is stale and cannot be used as a staging gate. Merging this PR ships to real users immediately.

How to manually test it

Prerequisites. NEXT_PUBLIC_SENTRY_DSN must be set in the target environment before the build — it is inlined at build time, so setting it afterwards changes nothing until a rebuild. It is present in Production and Preview as of 2026-07-30. Sentry project: bmr-p0 / guitar-crm (EU region, de.sentry.io).

Locally, before deploying

Step 1 Confirm the DSN reaches the browser bundle

npm run build
grep -rl "ingest.de.sentry.io" .next/static/ | head

Expected: at least one chunk listed. Before the fix this returned nothing at all — that silence is the entire bug.

Step 2 Confirm the ratchet test guards the convention

npx jest __tests__/architecture/sentry-client-instrumentation.test.ts

Expected: 5 passing. To see it actually bite, rename the file back (git mv instrumentation-client.ts sentry.client.config.ts) and re-run — 4 of 5 should fail, then rename it forward again.

Against a deployed build

Step 3 Confirm the SDK is live in the page

Open the deployment, then in DevTools console:

typeof window.__SENTRY__   // expect "object"  (was "undefined")

Expected: "object". If it is still "undefined", the build predates the DSN env var or the rename did not ship.

Step 4 Confirm a real browser error arrives in Sentry

In the DevTools console on the deployed site:

setTimeout(() => { throw new Error("manual test: client error boundary check"); }, 0);

Expected: within ~30s the issue appears at bmr-p0 → guitar-crm, tagged environment: production (or preview), with a readable un-minified stack trace — source maps upload on every build. Delete the test issue afterwards.

Edge case worth checking: an ad-blocker. Requests go through the /monitoring tunnel specifically to survive blockers; confirm in the Network tab that a POST to /monitoring?o=…&p=…&r=de returns 200 with a JSON {"id":"…"} body. A response containing HTML instead means the query params were dropped and the request fell through to the app.

Step 5 Confirm an error boundary reports

Navigate between a few pages, then trigger any genuine client-side failure (e.g. load a detail page for an id that does not exist). Expected: the error boundary renders its fallback UI and a corresponding issue lands in Sentry. Before this fix the fallback still rendered and nothing was ever reported — which is exactly why the gap went unnoticed.

What this does not cover

  • Server-side delivery was verified by construction, not observation. The server config compiles into the build, instrumentation.ts registers it and exports onRequestError, and the ingest endpoint is confirmed reachable — but no app-thrown server error was watched arriving, because the available Sentry token is project:releases-scoped and cannot read events.
  • Preview cannot be used as a gate while ignoreCommand cancels non-production builds, so steps 3–5 effectively run against production.
  • Sentry quota impact of enabling replay + 10% tracing on real traffic is not measured here.
