Teacher edits and archives their own student

Date: 2026-11-27 · Issue: #1178 · Branch: feature/teacher-edits-own-student

What changed

  • Database — new SECURITY DEFINER function teacher_update_student(p_student_id, p_changes) (migration 20261127130000_teacher_update_own_student.sql). An admin, or a teacher who shares a non-deleted lesson with the student, may change the student-card columns (name, phone, level, instrument, start date, colour, parent name/e-mail, schedule, rate, billing cycle, notes) and student_status (archive / restore). Any other key — is_admin, is_teacher, is_active, email, parent_id … — is refused with 42501. Staff profiles and other teachers' students are refused. profiles policies are unchanged, so a direct UPDATE by a teacher still changes nothing.
  • API — PUT /api/users/[id] now admits teachers; their body goes to the RPC, never to a direct update. Admin-only body keys answer 403.
  • Edit page — /dashboard/users/[id]/edit lets in a teacher for a student they teach (server-side check, canEditStudent); others are still redirected to the card. The teacher form hides the role toggles and the account-active switch, and keeps the student status (archive).
  • Student card — "Edit" link and "Archive" (with confirmation) / "Restore" for admin and the student's teacher.
  • List — a teacher sees the heading "Students / Uczniowie" instead of "People / Osoby", no "Teachers / Admins" role filter options, no "Invite teacher" button, and an "Edit →" link on each of their students.

How to test (dev stack, after the migration reached StrummyDevelopment)

The migration is not applied by hand anywhere; it reaches dev when the PR merges into dev (or CI's RLS job applies it to its scratch run). Until then the teacher save answers 500 "function does not exist".

  1. Sign in as the dev teacher (TEST_TEACHER_EMAIL, default teacher@dev.local).
  2. Open /dashboard/users. Expected: heading "Students", role filter offers only All roles / Students / Unclaimed, no "Invite teacher"; every row has "Edit →".
  3. Open one of your students. Expected: "Edit" and "Archive" next to "Import songs" / "Chord map".
  4. Click "Edit". Expected: the edit form opens (no redirect), with no Admin/Teacher/Student checkboxes and no "Account active" switch; a Student status select is present.
  5. Change the name and level, Save. Expected "✓ Saved"; the card shows the new name and level.
  6. Back on the card click "Archive" → confirm. Expected: the button turns into "Restore"; the list's "Archived" status filter shows the student. Click "Restore" → back to active.
  7. Open /dashboard/users/<id of a student you do NOT teach>/edit. Expected: redirected to the card; the card has no Edit/Archive.
  8. From the browser console (signed in as the teacher): fetch('/api/users/<own student id>',{method:'PUT',headers:{'Content-Type':'application/json'},body:JSON.stringify({isAdmin:true})}) → 403. Same with {full_name:'x'} for a student you don't teach → 403.
  9. Sign in as admin: the list still says "People", shows all filters, and the edit form still has the role toggles.

Known limits

  • "My student" means a shared lesson (teacher_students). A student a teacher just added has no lesson yet, so they cannot edit or even see them in the list until the first lesson (#1073, unchanged).
  • E-mail is not editable by a teacher (the edit form never showed it; changing a signed-in account's e-mail needs the auth admin).
  • F02.1–F02.4 (add + invite) still run as admin; only the new F02.6 runs as the teacher.
