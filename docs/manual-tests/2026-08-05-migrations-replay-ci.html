Manual test — migrations-replay CI check

Date: 2026-08-05 · Branch: fix/ci-restore-hosted-quality-gates · Scope: CI / database

What was built

A third schema check for the self-hosted CI, answering a question the existing two cannot: does supabase/migrations actually rebuild the schema that is running?

Check Compares State
db-parity production schema ↔ development schema existed
types-drift database.types.ts ↔ live dev schema existed
migrations-replay migration chain ↔ live dev schema new

The gap mattered because a change applied by hand through psql or Studio lands in dev, gets copied to prod, appears in the generated types — and is invisible to all three of those checks. Only building a database from scratch finds it.

How it works

  1. Creates a throwaway database inside the dev Postgres container (dropped again on exit, via a shell trap).
  2. Installs fixture schemas extensions, auth, storage — owned by the Supabase services, not by our chain. Dumped in two pg_dump sections; post-data statements referencing public. are filtered out (those are our triggers on auth.users, which the chain itself creates moments later).
  3. Replays every supabase/migrations/*.sql in filename order, aborting on the first failure.
  4. pg_dump --schema-only -n public of the result, diffed against the same dump of live dev.

Neither production nor the dev postgres database is ever written to.

Files

  • scripts/e2e-remote/schema-dump.lib.sh — new; shared normalize(), dump_public_schema(), require_container()
  • scripts/e2e-remote/check-migrations-replay.sh — new; the check itself
  • scripts/e2e-remote/check-db-parity.sh — refactored onto the shared lib (its inlined normalize() was about to become a second copy)
  • .github/workflows/e2e.yml — new migrations-replay job on the e2e-light runner, guarded by needs.guard.outputs.trusted, ungated like db-parity
  • .github/workflows/README.md — documents the three-check triangle

How to test it manually

Prerequisites: on the Orange LAN (or via Tailscale), the StudentDevelopment Supabase stack up on uwh.

1. Happy path — run the check

rsync -a --delete scripts/e2e-remote supabase/migrations uwh:~/replay/   # or just run it on a CI checkout
ssh uwh 'cd ~/replay && bash scripts/e2e-remote/check-migrations-replay.sh /tmp/replay.diff'

Expected on a healthy chain:

Replaying 58 migrations into strummy_migration_shadow (scratch, inside supabase_db_StudentDevelopment)...
OK: replaying supabase/migrations reproduces the development schema exactly.

As of 2026-08-05 this is NOT what happens — see “Known findings” below. The current expected output is a FAILED: line naming 20260723150000_parent_read_repertoire_preferences.sql.

2. Confirm it is genuinely read-only

# before and after the run, this must print nothing:
ssh uwh "docker exec supabase_db_StudentDevelopment psql -U postgres -d postgres -tAc \
  \"select datname from pg_database where datname like '%shadow%'\""

The scratch database must not survive the run — the trap drops it even on failure. Verified.

3. Prove it catches an unfiled change (the whole point)

Apply something to dev without writing a migration, then re-run:

ssh uwh "docker exec supabase_db_StudentDevelopment psql -U postgres -d postgres \
  -c 'create table public.zz_unfiled_probe(id int)'"
# re-run the check → must fail with a '>' line for zz_unfiled_probe
ssh uwh "docker exec supabase_db_StudentDevelopment psql -U postgres -d postgres \
  -c 'drop table public.zz_unfiled_probe'"

Read the diff direction as: < = only from migrations, > = only in live dev.

4. Regression check on the refactored sibling

ssh uwh 'cd ~/replay && bash scripts/e2e-remote/check-db-parity.sh /tmp/parity.diff'

Must behave exactly as before the refactor. Verified 2026-08-05: reports the pre-existing 8-line prod/dev drift (four functions missing SET search_path TO 'public', 'pg_temp' on prod) — unrelated to this change, and exactly what it reported beforehand.

5. CI wiring

  • Open a PR — migrations-replay should appear and run without a label (ungated).
  • On failure, the migration-replay-diff artifact holds both the schema diff and the full psql log.
  • Do not add it to branch protection as a required check until it is green.

Known findings — the check is currently red

It found real defects on its first run. All three block replay on a fresh database; none of them affect the running dev or prod stacks.

  1. 20260723150000_parent_read_repertoire_preferences.sql (uncommitted edit) and 20260727130000_legacy_policies_profile_space.sql (committed) were rewritten from user_id to profile_id on the reasoning that “the original SQL fails outright”. At their position in the chain that column really is called user_id — the rename happens later, in 20260731143000_rename_profile_fk_columns.sql, and Postgres rewrites policy predicates automatically on ALTER … RENAME COLUMN. So the live policies read profile_id as a consequence of the rename, not as evidence the migrations never ran. Verified empirically: reverting both files to user_id lets the chain proceed past this point.
  2. 20260802150000_system_ai_teacher.sql inserts the AI-coach profile with user_id = NULL and no is_shadow, violating the baseline's ck_shadow_user_id CHECK. The row exists in dev and prod (inserted before the constraint, or by hand), so the file cannot reproduce it.
