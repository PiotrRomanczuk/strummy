Production auth email — restored

Date: 2026-08-06 · Branch: fix/gotrue-email-templates

What was broken

Every authentication email on strummy.online failed. Sign-up showed "Error sending confirmation email" and returned HTTP 500; password reset, student invites, magic links and email-change were dead the same way. No mail left the server.

Root cause. supabase/config.toml declared email templates via content_path. The Supabase CLI turns each of those into a Kong URL — http://supabase_kong_StudentProduction:8088/email/confirmation.html — and sets GOTRUE_MAILER_TEMPLATES_* to it. Kong serves nothing there: no /email route in kong.yml, and docker inspect shows Mounts: []. GoTrue treats a failed template fetch as a failed send, so the whole request fails. The config.toml comment had called this a "local dev quirk" since June; production had it too.

What changed

File Change
public/email/*.html The five templates moved here from supabase/templates/. The app serves them, so no Kong dependency.
supabase/config.toml content_path removed so the CLI stops re-adding Kong URLs on restart. Subjects stay — GOTRUE_MAILER_SUBJECTS_* works fine.
scripts/ops/restore-gotrue-mail-urls.py Now owns GOTRUE_MAILER_TEMPLATES_* too, plus --drop-templates to fall back to GoTrue's built-in bodies.
docs/runbooks/supabase-stack-restart.md New section 3 documenting the failure and how to verify a real send.
playwright.prod.config.ts, tests/prod-global-setup.ts Deployed-target E2E config: validates accounts up front, drops the destructive teardown.

How to verify

1. Container env is clean

ssh uwh 'docker exec supabase_auth_StudentProduction env | grep MAILER_TEMPLATES'

Expect no output (built-in bodies) or five https://strummy.online/email/*.html URLs once this branch is deployed and the repair script is re-run without --drop-templates.

2. No template errors in the log

ssh uwh 'docker logs supabase_auth_StudentProduction --since 10m 2>&1 | grep templatemailer_template_body_http_error'

Expect nothing. Before the fix this printed a 404 line per mail type, every attempt.

3. A real sign-up (the only proof that counts)

  1. Open https://strummy.online/sign-up.
  2. Register with an alias you control, e.g. p.romanczuk+mailcheck@gmail.com.
  3. Expected: the "check your email" screen, not a red error under the form.
  4. Expected: the message arrives, and its link points at db.strummy.online (not 127.0.0.1).

4. Automated

E2E_SKIP_AUTH_PREFLIGHT=1 PLAYWRIGHT_BASE_URL=https://strummy.online \
  npx playwright test --config=playwright.prod.config.ts \
  --project="Desktop Chrome" -g "email verification screen"

Also confirm the smoke gate still passes (14 tests, ~11s):

E2E_SKIP_AUTH_PREFLIGHT=1 PLAYWRIGHT_BASE_URL=https://strummy.online \
  npx playwright test --config=playwright.prod.config.ts \
  --project="Desktop Chrome" --grep @smoke
Still open — this fix alone does not restore sign-up. With the templates repaired, the next send reached SMTP and Gmail rejected it: 550 5.4.5 Daily user sending limit exceeded. All product email — GoTrue auth and the app's own notifications and cron dispatcher (lib/email/smtp-client.ts) — goes through one personal Gmail account, sharing a single ~500/day cap. Until that moves to a transactional provider, sign-up stays broken whenever the cap is hit.

Edge cases worth checking

  • Password reset and student invite — same mailer, same fault; both should work once quota allows.
  • After any supabase stop/start — re-run the repair script; the CLI reverts these vars every time.
  • Template rendering — with --drop-templates in force the emails are GoTrue's plain defaults, not the branded ones. Expected until this branch deploys.
