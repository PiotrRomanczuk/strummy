Deleting a user no longer fails with a database error

2026-07-30 · branch fix/audit-trigger-search-path · migration 20260730103000_pin_audit_trigger_search_path.sql

What was wrong

Deleting any user through the Auth admin API returned 500 "Database error deleting user". Underneath, Postgres raised type "audit_action" does not exist. So user deletion was simply broken — in production and in dev — and had been for as long as those triggers have existed.

The cause is a search_path mismatch. The four tr_audit_* functions are SECURITY DEFINER but never pinned their search_path, so they inherit the caller's. GoTrue connects as supabase_auth_admin, whose role config is search_path=auth — public is not in it. Deleting an auth.users row cascades to public.profiles (via profiles_user_id_fkey ON DELETE CASCADE), which fires tr_audit_profiles, which references the audit_action type and the audit_log table unqualified. Neither resolves, the trigger aborts, and it takes the whole delete transaction down with it.

Why nobody noticed: deleting via psql as postgres works fine — that role's search_path includes public. The bug only appears through the Auth API. Any test that cleaned up with psql would have masked it completely.

What changed

One migration, four ALTER FUNCTION … SET search_path = public, pg_temp statements. Function bodies are untouched. The DO block skips any function that isn't present, so the migration is replayable against a partially-built database.

pg_temp is listed last deliberately: Postgres searches the temporary schema first unless it appears explicitly, so a caller able to create temp tables could otherwise shadow the unqualified audit_log relation these functions write to and divert audit rows. That closes a second, latent problem alongside the crash.

Verified on StudentDevelopment

Check Before After
DELETE /auth/v1/admin/users/<id> 500 — Database error deleting user 200 — deleted
Profile row cascade-removed no (transaction aborted) yes
audit_log row for the delete never written written (entity_type=profile, action=deleted)

That last row is the important one: the goal was to make the trigger work, not to make the error go away by skipping the audit.

How to test it yourself

1. Automated (fastest)

Two regression tests were added. They delete through the admin API specifically — not psql — which is the whole point. 

npx jest --config jest.config.rls.ts \
  lib/testing/rls/__tests__/audit-trigger-search-path.rls.test.ts

Expected: 2 passed. They need the dev stack reachable (NEXT_PUBLIC_SUPABASE_LOCAL_URL=http://192.168.1.75:55321 from .env.local); without keys the suite skips rather than fails. The harness hard-refuses to run against production.

2. By hand, against the dev stack

  1. Confirm the precondition — the auth role has no public: 
    ssh uwh "docker exec supabase_db_StudentDevelopment psql -U postgres -d postgres \
  -c \"select rolconfig from pg_roles where rolname='supabase_auth_admin';\""
    Expect search_path=auth.
  2. Confirm the fix is applied: 
    ssh uwh "docker exec supabase_db_StudentDevelopment psql -U postgres -d postgres \
  -c \"select proname, proconfig from pg_proc p \
      join pg_namespace n on n.oid=p.pronamespace \
      where n.nspname='public' and proname like 'tr_audit%';\""
    Expect {search_path=public, pg_temp} on all four rows.
  3. Create a throwaway user, then delete it via the API and watch for 200 rather than 500. Both steps are scripted in repro_delete_bug.sh from the session scratchpad.
  4. Then check an audit row landed: 
    select entity_type, action, created_at from public.audit_log
where entity_type = 'profile' order by created_at desc limit 5;

3. Through the UI

Sign in as an admin, open Students, and delete a throwaway student created for the purpose. Before this fix that action failed with a server error; it should now complete. Use a disposable account, not real student data.

Edge cases worth a look

  • Replay safety — run the migration twice; the second run is a no-op (ALTER FUNCTION is idempotent, and missing functions are skipped with a notice rather than an error).
  • Audit still attributes correctly — delete a profile while signed in as an admin (not service role) and confirm audit_log.actor_id is that admin's profile id, not null.
  • The other three triggers — only tr_audit_profiles sits on the auth cascade, so the crash surfaced there. Exercise assignments / lessons / song-progress writes to confirm those still audit normally after the change.

Not covered by this change

29 of 53 SECURITY DEFINER functions in public still have no pinned search_path. Only these four are reachable from supabase_auth_admin, so only these four were in scope. The remaining 25 are the same latent hazard and are worth a follow-up sweep.
