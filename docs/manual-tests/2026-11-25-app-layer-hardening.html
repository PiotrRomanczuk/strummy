Application-layer hardening

Date: 2026-11-25 · Branch: fix/app-layer-hardening → dev · Scope: auth callback, secret checks, server-only modules, notification actions, cron email jobs, shadow-profile linking

What changed

Area Before After
/auth/callback The next parameter was appended to the origin as given. next goes through postLoginPath(): only /dashboard… paths and the exact path /reset-password (used by the password-reset email) are kept; anything else lands on /dashboard on the same host.
Cron bearer, Google Calendar channel token Compared with === / !==. New lib/auth/secret-compare.ts (secretsMatch): length check, then crypto.timingSafeEqual. Used by verifyCronSecret and the calendar webhook.
POST /api/admin/set-passwords Bulk password utility authorised by the service-role key. Deleted, with its test and Bruno request. Nothing in the app, scripts or docs called it.
Six lib/ modules Marked 'use server' (auth-event logger, bounce handler, in-app notifications, notification service, queue processor, monitoring). import 'server-only' instead. New guard __tests__/architecture/lib-server-actions.test.ts fails if any lib/ file declares 'use server' again.
app/actions/in-app-notifications.ts getInAppNotifications(userId) returned that profile's rows for any caller. Returns [] unless userId is the caller's own profile. The unused getUnreadNotificationCount was removed.
Morning briefing + weekly insights emails Server actions in app/actions/email/ with no auth check. Moved to lib/email/send-admin-report.ts and lib/email/send-weekly-insights.ts as server-only modules. Their only callers are the cron routes, which check CRON_SECRET.
POST /api/admin/link-shadow-user Any teacher could link any shadow profile to any account, and its "account already has a profile" check looked at profiles.id instead of user_id, so the reference transfer could run before the insert failed. Deleted, with its helpers, tests and Bruno request. Nothing called it: since S2, handle_new_user claims the shadow profile in place at sign-up.
Connecting Google (/api/auth/google → /api/oauth2/callback) The start route sent anyone to Google's consent page without a state; the callback stored the tokens for whoever was signed in, whatever browser started the flow. The start route needs a signed-in user (otherwise 307 to /sign-in), puts a random state in an httpOnly, SameSite=Lax cookie scoped to /api/oauth2/callback (10 min, Secure over https) and sends it to Google. The callback expires the cookie and accepts the code only when the returned state matches it (constant time); otherwise /dashboard?error=google_auth_state before any lookup.
Calendar webhook without a secret CALENDAR_WEBHOOK_SKIP_TOKEN=true accepted notifications with no token check. The flag is gone: without GOOGLE_CALENDAR_WEBHOOK_SECRET every notification gets 401, in every environment.

How to test manually (dev stack)

Prerequisites: npm run dev against the StrummyDevelopment stack, the dev role accounts from CLAUDE.local.md, and CRON_SECRET / GOOGLE_CALENDAR_WEBHOOK_SECRET in .env.local.

1. Sign-in and password reset still land in the right place

  1. Sign out, open /dashboard/songs, sign in: you land on /dashboard/songs.
  2. On /forgot-password request a reset for the student account and open the link from the email: you land on /reset-password and can set a new password.
  3. Open /auth/callback?code=x&next=/sign-out: with an invalid code you get /auth/auth-code-error; the redirect target only matters after a valid code, and is covered by the unit tests for each rejected shape.

2. Cron secret

curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $CRON_SECRET" localhost:3000/api/cron/daily-report   # 200
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer wrong" localhost:3000/api/cron/daily-report            # 401
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/api/cron/weekly-insights                                          # 401

Expected: the morning briefing email is sent only on the first call.

3. Calendar webhook token

curl -s -X POST localhost:3000/api/webhooks/google-calendar \
  -H 'x-goog-channel-id: c1' -H 'x-goog-resource-id: r1' -H 'x-goog-resource-state: sync' \
  -H "x-goog-channel-token: $GOOGLE_CALENDAR_WEBHOOK_SECRET"     # {"status":"ok"}
# same request with a wrong token                                 # 401

Then remove GOOGLE_CALENDAR_WEBHOOK_SECRET, set CALENDAR_WEBHOOK_SKIP_TOKEN=true, restart and send the first request again: 401 (the flag no longer does anything).

4. Notifications

  1. As the teacher, open /dashboard/notifications: your notifications and the unread badge show as before.
  2. Scroll to load the next page and mark one as read: both still work.

5. The removed routes

POST /api/admin/set-passwords and POST /api/admin/link-shadow-user now return 404. A shadow student who signs up with their invite email still lands on their existing lessons (the database trigger does that, unchanged here).

6. Connecting Google

  1. Signed out, open /api/auth/google: you land on /sign-in.
  2. Signed in as the teacher, Settings → Integrations → Connect. The Google consent URL has a state= parameter; DevTools → Application → Cookies shows strummy_google_oauth_state (HttpOnly, path /api/oauth2/callback, same value).
  3. Approve: you land on /dashboard?success=google_connected and the cookie is gone.
  4. Press Back to replay the callback URL: /dashboard?error=google_auth_state (the state works once).
  5. Copy the /api/oauth2/callback?code=…&state=… request URL from DevTools → Network after step 3 and open it in another browser where you are signed in as the student: ?error=google_auth_state (that browser has no state cookie), and the student has no Google integration afterwards.

No browser screenshots: this change is server-side only and was verified with unit tests, typecheck, lint and the structure check, not in a browser session.
