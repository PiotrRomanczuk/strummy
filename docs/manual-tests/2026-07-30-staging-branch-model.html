A staging gate, on git

Date: 2026-07-30  ·  Branch: chore/staging-branch-model  ·  Scope: branch model, Vercel build triggers, release job, docs

What was actually done

Until today main was Vercel's production branch, so merging any feature PR shipped straight to real users — and preview deployments were cancelled outright, so there was no way to look at a change first. That is how a build with completely dead client-side error reporting reached production on 2026-07-29 and stayed there.

New model: main is staging, production is production.

feature/x ──PR──▶ main ─────────────▶ production │ │ ▼ ▼ staging deploy strummy.vercel.app (Vercel Auth protected) + strummy.app tag + GitHub Release crons run here only

The changes

File Change
vercel.json ignoreCommand now matches on VERCEL_GIT_COMMIT_REF instead of VERCEL_ENV, so only main and production build. Feature branches and PRs cost zero build minutes and produce no URL. (exit 1 = build, exit 0 = skip — the inversion is Vercel's.)
.github/workflows/ci.yml Triggers extended to production. The release job now only runs on pushes to production, so merging a feature PR no longer cuts a tag. Release-PR bump defaults to minor (a batch usually contains a feature); labels still override. Added a fallback: a push with no associated PR now tags with auto-generated notes instead of silently skipping — an untagged production deploy is worse than an imperfectly-titled release.
.github/workflows/e2e.yml Push trigger extended to production. Label gating unchanged, billed minutes still zero.
CLAUDE.md, .claude/rules/workflow.md Deployment + workflow docs rewritten for the two-stage model, including the release-notes consequence below.
Release notes semantics change. One release now covers several feature PRs, because the release is the main → production PR and its body is what GitHub publishes. Keep writing good feature-PR bodies — they're where the detail lives — but write the release PR as a summary of the batch.
Staging shares the PRODUCTION database. This was a deliberate choice: it's a smoke gate for code, not a safe playground. Writes on staging touch real student data and migrations cannot be rehearsed there. Vercel Authentication (SSO protection, currently enabled for all_except_custom_domains) is the only thing keeping the staging URL from being a public second door into production data — do not disable it. If you later want a real playground, the upgrade is pointing staging at its own database.

Verified before pushing

  • vercel.json parses; ignoreCommand simulated against real branch names — BUILD for production and main, skip for feature/*, fix/*, chore/*, dependabot/*.
  • Both workflow YAML files parse; release.if resolves to github.event_name == 'push' && github.ref == 'refs/heads/production'.
  • Bump logic dry-run from v0.160.0: main→v0.161.0 (minor), main+version:patch→v0.160.1, main+version:major→v1.0.0, fix/hotfix→v0.160.1 (patch).

Rollout — do these in order

The config is order-tolerant on purpose: the ignoreCommand keys off the branch name, so main builds whether it is currently Vercel's production branch or not. Nothing stops deploying at any point in this sequence.

Step 1 Merge this PR to main

While main is still Vercel's production branch, this deploys to production as usual — same app code, new build config. No release is cut (the release job now requires production).

Step 2 The production branch is created at the currently-live commit

Created from main at 89fa5908 — the exact commit serving users now — so production starts identical to what is already live. No deploy results (Vercel's production branch is still main at this point, and preview builds for it are skipped).

Step 3 — you Flip Vercel's Production Branch

Vercel → strummy → Settings → Git → Production Branch: change main to production. This is the one step that cannot be done from the CLI. Until you do it, main still ships to real users and there is no staging gate.

The currently-aliased production deployment keeps serving throughout — the alias only moves when a new production deployment is promoted.

Step 4 — you Give Preview the 12 missing env vars

Staging builds as VERCEL_ENV=preview, and Preview is currently missing 12 of Production's 23 variables — including every Supabase credential. Without this, staging will build and then be completely dead: no database at all.

Missing: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, SUPABASE_JWT_SECRET, GOOGLE_REDIRECT_URI, SPOTIFY_CLIENT_ID, SPOTIFY_CLIENT_SECRET, SPOTIFY_REDIRECT_URI, SPOTIFY_USER_REFRESH_TOKEN, DEMO_WRITES_ENABLED, NEXT_PUBLIC_AVATAR_UPLOAD_ENABLED.

Easiest route: in the Vercel dashboard, edit each of those variables and tick Preview alongside Production. No value re-entry, and no secrets touch your disk — which is why this wasn't scripted (vercel env pull would have written production secrets to a file).

Sanity check afterwards:

npx vercel env ls preview | grep -c SUPABASE   # expect the Supabase set present

Step 5 First release: main → production 

gh pr create --base production --head main \
  --title "Release: staging branch model" --body "…batch summary…"

Expected on merge: CI runs on production, a tag is cut (v0.161.0 — minor by default), a GitHub Release appears with that PR's body, and a production deployment takes the strummy.vercel.app alias.

How to verify the gate actually works

Test 1 A feature branch produces no build

Push any fix/* branch and open a PR. Expected: GitHub CI runs, but Vercel reports no deployment (or an immediately-skipped one). Previously every PR produced a cancelled build; now it produces none.

Test 2 Merging to main deploys staging, not production 

# note the production deployment id before merging
npx vercel inspect https://strummy.vercel.app | grep -E "id|created"

Expected after merging a PR to main: a new deployment appears with environment Preview, and the id behind strummy.vercel.app is unchanged. Opening the staging URL should prompt for Vercel Authentication. No tag, no GitHub Release.

Test 3 Merging to production releases

Expected: environment Production, the strummy.vercel.app id changes, a new tag and Release exist, and /api/health/live returns 200 on the live domain. 

curl -s https://strummy.vercel.app/api/health/live

Test 4 Crons stay on production only

Expected: the Vercel dashboard lists the cron against the production deployment, and staging deployments show none. This is what stops staging from emailing your students.

What this does not cover

  • Branch protection on production is not configured — nothing yet forces the quality gate before a release merge. Worth adding (Lint, types, tests, build as required), and it also blocks accidental direct pushes.
  • A stable staging alias (e.g. strummy-staging.vercel.app) is not assigned; staging is reachable at its generated deployment URL and the strummy-git-main-… alias.
  • Migration rehearsal remains impossible while staging shares the production database — that is the known limit of the choice, not an oversight.
  • Hobby serializes production builds. Observed 2026-07-30: one wedged build blocked the queue for 31 minutes and had to be cancelled before a queued deploy would start. If a deploy seems not to happen, look for a stuck build first.
