Manual test report · invite recovery · production behaviour change

An expired invite is no longer a dead end

Date: 2026-07-31  ·  Branch: feature/resend-invite  ·  Touches: a new profiles_signed_in database function, the People list, the student detail page, and the email-link lifetime on the production auth stack.

The problem

An invite was sent to a student at 22:41. It was opened the next morning and had already expired: 

Your invitation link has expired. Please ask your teacher to send a new invite.

The teacher could not do that. Once an invite is sent, the profile stops being a shadow — and every invite affordance in the UI was keyed off exactly that flag, so the button disappeared. The message told the student to ask for something the product could not provide.

Root cause: the app used is_shadow as its definition of “unclaimed”. But sending an invite creates the auth account and clears is_shadow, while the person still has not signed in. So the two meanings come apart at precisely the moment they matter, and an invited-but-unclaimed student was indistinguishable from a fully onboarded one.

What changed

1 · A real signal for “has this person ever signed in”

The honest answer lives in auth.users.last_sign_in_at, which the authenticated role cannot read. A new SECURITY DEFINER function answers the question for a caller-supplied set of profile ids without exposing the auth schema, and refuses anyone who is not an admin or teacher. 

public.profiles_signed_in(p_profile_ids uuid[]) returns table (profile_id uuid)

It returns only the ids that have signed in, so “absent” means unclaimed. The older profiles.sign_in_count / last_sign_in_at columns were deliberately not resurrected — they were denormalised copies that went stale, and dropping them is what broke the invite flow in the first place.

2 · A Resend invite button

Both the People list and the student detail page now offer an invite to anyone who has never signed in — whether or not one has already been sent. For an already-invited profile the address is already on the row, so it dispatches straight to sendUserInvite rather than re-running the shadow path (which would wrongly write invite_email onto a non-shadow profile).

No server-side change was needed: sendUserInvite already refused only people who have actually signed in. The capability existed; the UI just never offered it.

3 · Email links now last 24 hours

otp_expiry raised from 3600 to 86400 on the production auth stack, so a link sent in the evening still works the next morning.

This setting is global. It governs magic links, email confirmation, email change and password recovery too — not just invites. A password reset link now stays valid for a day, which is a real widening of that window and the reason Supabase warns about values above an hour. It is an accepted trade here: the resend path above is what actually fixes the invite problem, and this only helps people who come back to the email late.

How to verify by hand

  1. Sign in as a teacher and open /dashboard/users.
  2. Expected: Michal, Ola and Quentin each show “Resend invite →” on the right. Kuba does not, because he has signed in.
  3. Click Resend invite on one of them. Expected: it flips to “✓ Sent” and a fresh invite email arrives.
  4. Open the student's detail page (/dashboard/users/<id>). The same button appears in the header actions.
  5. Open the emailed link. Expected: it works, and it still works if opened many hours later — up to 24h rather than 1h.

Edge cases worth checking

  • A student who has signed in. No button. If the action is somehow invoked, the server still refuses with “User has already signed in — no invite needed”.
  • A shadow profile with no invite email. Unchanged — it uses the existing “set an address then invite” flow, not the resend path.
  • A deactivated profile. No invite offered; re-inviting someone who was deliberately switched off would be wrong.
  • If the helper function fails (permissions, outage) the UI degrades to treating everyone as unclaimed — at worst a redundant resend button, never a student hidden from view. There is a test for this.

Applying the auth change — and a warning

GoTrue reads MAILER_OTP_EXP from its environment at boot, and the Supabase CLI bakes that env in at container-creation time. So the config edit only takes effect after the containers are recreated.

The obvious shortcut does not work. Removing just the auth container and running supabase start does not bring it back — the CLI sees the stack as already running and skips it, leaving auth down. This was discovered by rehearsing on the dev stack first; doing it straight on production would have taken authentication offline with no quick way back. The working procedure is a full supabase stop && supabase start, which restarts Postgres too.

Both stacks were updated and verified afterwards: dev came back with 3 828 profiles intact, production with 7 profiles / 50 lessons / 465 songs / 80 repertoire rows — unchanged — and strummy.online plus the database tunnel both answering 200. The previous config is saved on the host as config.toml.bak-otp-20260731.
