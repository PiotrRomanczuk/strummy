Notification queue drained every 10 minutes (#1215)

Date: 2026-11-27 · Branch: feature/notification-queue-timer → dev · No browser used (backend + ops change)

What changed

  • Before: the only trigger of /api/cron/process-notification-queue was the daily Vercel dispatcher (06:00 UTC). Mail scheduled "1 hour after the lesson", "immediate" cancellations and retries waited until the next morning.
  • New trigger: scripts/ops/notification-queue/ — a systemd user timer for uwh (:05, :15 … :55) runs trigger.sh prod, which GETs the route on strummy.online with the same CRON_SECRET bearer as the dispatcher. The secret is read from a mode-600 file on the host and passed to curl on stdin.
  • Backlog report: the route now returns backlog: { overdue, oldestDueAt, oldestAgeMinutes, isStale } — rows still pending more than 60 min after scheduled_for, read after the drain (lib/notifications/queue-backlog.ts).
  • Alarm: the script exits 1 when the call fails or isStale is true; the unit's OnFailure=unit-failure-mail@%n.service (home-ops notifier) mails the journal. Repeats at most every 6 h while the problem lasts.
  • Route header no longer claims "every 15 minutes". The never-activated scripts/cron/ (whose daily mode would now double-fire next to the dispatcher) is removed; the cron-debugger skill and blueprint 07 point at the new directory.
  • Not installed yet. Installation on uwh happens after the change reaches main — steps in scripts/ops/notification-queue/README.md.

How to test manually — dev stack + Mailpit (F10.4)

Prerequisites: Mac on the home LAN; .env.local pointing at StrummyDevelopment with CRON_SECRET, SMTP_HOST at the dev Mailpit and STUDENT_EMAILS_ENABLED=true (the same setup Core flows F10.4 needs).

  1. Start the app on this branch: npm run dev (http://localhost:3000).
  2. Check the route by hand; expect success:true and a backlog object: 
    curl -s -H "Authorization: Bearer $(grep ^CRON_SECRET= .env.local | cut -d= -f2-)" \
  http://localhost:3000/api/cron/process-notification-queue | python3 -m json.tool
    Without the header: 401 Unauthorized.
  3. Configure a dev instance for the script in a throwaway directory (never commit these files): 
    D=$(mktemp -d); echo 'STRUMMY_BASE_URL=http://localhost:3000' > $D/notification-queue-dev.env
(umask 077; grep ^CRON_SECRET= .env.local | cut -d= -f2- > $D/notification-queue-dev.secret)
STRUMMY_QUEUE_CONFIG_DIR=$D XDG_STATE_HOME=$D/state scripts/ops/notification-queue/trigger.sh dev; echo "exit=$?"
    Expected: [notification-queue dev] ok sent=… overdue=0, exit=0.
  4. Delivery within 15 minutes (F10.4): run the flow, which inserts a queued reminder for the flow student and drains it the way the timer does: 
    npm run test:flows -- --grep "F10.4"
    Expected: pass; the mail "Upcoming Lesson Reminder" is in Mailpit and the queue row is sent. To see it end to end with the script instead of the spec: insert a pending row with scheduled_for = now() for a dev student (admin client / Studio on the dev stack only), run step 3's command, and open Mailpit — the mail is there at once; on uwh the next timer tick is at most 10 minutes away.
  5. Alarm: insert a pending row with scheduled_for = now() - interval '2 hours' for a recipient whose mail is skipped or failing (or stop the drain by pointing SMTP_HOST at nothing), run step 3: expect a stale … overdue=1 age_min=120 line, ALARM, exit=1; run again: "alarm already raised … not repeating yet", exit=0. Delete the row afterwards (dev stack is shared).
  6. Clean up: rm -rf $D.

After merge to main — production (owner, on uwh)

  1. cd ~/strummy-prod-e2e/checkout/scripts/ops/notification-queue && ./install.sh
  2. From the Mac: secret strummy-prod-cron-secret | ssh uwh 'umask 077 && cat > ~/.config/strummy/notification-queue-prod.secret' (create the Bitwarden item first if it does not exist — README).
  3. ./trigger.sh prod; echo $? → ok … overdue=0, 0. Then ./install.sh --enable.
  4. journalctl --user -u strummy-notification-queue -n 20 after 10–20 minutes shows a line per run.
  5. Then close #1215.

Edge cases worth a look

  • Rows scheduled in the future (lesson recap +1 h) are not "late" — age is measured from scheduled_for.
  • Production before the route change reaches main: the script logs backlog=unreported and still exits 0.
  • The 06:00 UTC dispatcher and the timer never drain at the same moment (timer fires at :05).
