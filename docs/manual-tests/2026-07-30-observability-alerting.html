Monitoring that can interrupt you, instead of waiting to be checked

Date: 2026-07-30  ·  Branch: fix/observability-alerting  ·  Scope: cron monitor check-ins, dispatcher status code, public liveness probe

What was actually done

An audit of the monitoring stack found six observability channels and effectively zero automated alerting. Every channel was pull-based — Sentry, the system_logs viewer, /api/health, the debug dashboard — meaning someone had to go and look before anything was noticed. This closes the two specific holes that made that dangerous.

1. The daily cron fleet could stop entirely and nothing would say so

Every scheduled job in the system rides one Vercel cron (Hobby allows a single definition): /api/cron/dispatcher fans out to 15 jobs in-process. A job that throws was already reported — logger.error calls captureException — but a cron that never fires produces no error to capture. That failure mode was pure silence, and it covers lesson reminders, notification delivery, calendar sync and the GDPR cleanup.

The dispatcher now checks in to a Sentry cron monitor (cron-dispatcher, crontab 0 6 * * *, 30-minute margin, UTC): in_progress on entry, ok/error on exit. Sentry alerts on a missed check-in — which also catches "Sentry is misconfigured", because from Sentry's side both look identical: nothing arrived. That is precisely the class of failure that hid a dead client SDK for weeks.

Two subtleties worth knowing: automaticVercelMonitors: true cannot do this — it does not instrument App Router route handlers, which is every route here. And no check-in is recorded when verifyCronSecret fails, so a stranger hitting the URL cannot suppress the alert by faking a run.

2. The dispatcher answered 200 even when jobs failed

Individual cron routes deliberately return 200-with-an-error-payload (no paging on known-degraded states) and that stays. But the dispatcher is the fleet's single status signal, and an always-200 answer makes a broken run indistinguishable from a healthy one to any external prober. It now returns 500 when any job failed; deliberate no-ops are still excluded via skipped.

3. Nothing outside the app could check whether it was alive

/api/health is admin-only — 401 without a session — so no uptime monitor can poll it. New /api/health/live is unauthenticated and returns a single reachability bit: 200 when the app serves and its database answers, 503 otherwise. It deliberately leaks nothing (a test asserts the body has exactly status, database, checkedAt), because the underlying checker's message carries raw error text including LAN hosts and ports.

A plain "is the URL up" check is not a substitute: Next will happily return 200 for a shell page with a dead database behind it.

Verified before pushing: lint 0 errors · tsc 0 errors · full Jest suite green, including 3 new check-in tests and 5 new liveness tests. The existing dispatcher test that asserted 200 on a failed job was updated to 500 — that assertion change is the behavior change.

How to manually test it

Step 1 Liveness probe answers publicly

curl -i https://strummy.vercel.app/api/health/live

Expected: 200, body {"status":"ok","database":"up","checkedAt":"…"}, header Cache-Control: no-store. No session needed.

Confirm it leaks nothing: the body must contain exactly those three keys — no service names, no latency, no error strings, no host/port.

Step 2 Admin health stays protected

curl -s -o /dev/null -w '%{http_code}\n' https://strummy.vercel.app/api/health

Expected: 401. If this ever returns 200 unauthenticated, that is a leak — it exposes per-service error text and the cron registry.

Step 3 Dispatcher check-in creates the Sentry monitor

The monitor is created on first check-in (upsert), so it will not exist in Sentry until the dispatcher runs once. Trigger it manually with the cron secret: 

curl -i -H "Authorization: Bearer $CRON_SECRET" \
  https://strummy.vercel.app/api/cron/dispatcher

Expected: 200 with "success": true on a clean run, or 500 with "success": false and a jobs[] array naming what failed. Then check Sentry → Crons: a cron-dispatcher monitor should appear with one ok (or error) check-in and schedule 0 6 * * *.

Edge case: call it without the header — expect 401 and no new check-in recorded in Sentry.

Step 4 Arm the alert (manual, one-time — this is what makes it useful)

A monitor with no alert rule is still pull-based. In Sentry → Alerts, create a rule on the cron-dispatcher monitor for missed and error check-ins, delivered to email/phone. Until this exists, nothing about this change will reach you.

Step 5 Point Uptime Kuma at the liveness probe (manual, one-time)

Kuma runs on the Pi (https://pi.tail266853.ts.net). Add a monitor:

  • Type HTTP(s), URL https://strummy.vercel.app/api/health/live
  • Interval 60s, accepted status codes 200-299 only (so the 503 trips it)
  • Notification → your existing channel

This is the only monitor that survives the whole Vercel deployment being down, because it runs outside it. Requires your Kuma credentials, so it was not automated.
