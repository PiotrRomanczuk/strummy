Shadow-claim E2E ported to the S2 claim-in-place model

Date: 2026-07-27 · Branch: test/shadow-claim-carries-data · Scope: one E2E spec + one doc annotation. No application or schema code.

I could not run this spec. It needs a live Supabase stack, a service-role key, and the app served locally — none of which are available from this session. Everything below verifies statically (typecheck, lint, Playwright collection). Step 2 of "How to verify" is the one that actually matters and it is on you to run.

What was actually done

PR #525 was closed as superseded — its claim_shadow_profile() migration implemented a transfer-based claim that 20260727110000_handle_new_user_shadow_claim.sql ("S2") had already replaced with the opposite approach. One piece of it was worth keeping: the end-to-end regression test for the product's highest-value flow (ADR-0002) — a teacher tracks a student as a shadow profile with songs and lessons, the student signs up, and all that history must be on the account they log into.

That spec is ported here. Its user-visible assertions are unchanged; its database assertions were inverted, because the two models disagree about what a successful claim looks like.

Why the assertions had to flip

PR #525 (transfer) main, S2 (claim-in-place)
On signup INSERT a new profile with id = new.id UPDATE the shadow profile in place
Profile id changes never changes
FK references every table re-pointed, shadow deleted untouched — nothing to move
profiles.id vs auth.users.id welded equal deliberately independent

Concretely, in step 3 of the spec:

Old assertion New assertion Why
expect(claimedId).not.toBe(shadowId) expect(claimedProfileId).toBe(shadowId) The shadow row is the claimed profile now.
expect(claimed.user_id).toBe(claimed.id) expect(authUserId).not.toBe(profileId) S2 decouples the id spaces on purpose. Equality here would mean the pre-S2 model ran instead — so this assertion is now an active guard against regressing to it.
shadow row must be null removed — replaced by is_shadow === false and invite_email === null Nothing is deleted; the markers are cleared.
shadow_link_completed event logged removed Only claim_shadow_profile() emitted that event, and it does not exist on main.

Two further corrections that fall out of the id split:

  • auth.admin.updateUserById() and deleteUser() take the auth user id; the profiles and lessons/student_repertoire queries take the profile id. The old spec used one variable for both because the old model made them equal. They are now two variables and must not be collapsed.
  • afterAll no longer relies on an auth-user delete cascading to the profile — it deletes the seeded rows explicitly by profile id first, then removes the auth user. This also makes cleanup work when the run fails before the claim.

How to verify

1. Static checks (already run, reproduce in seconds)

npx tsc --noEmit                                            # clean
npx playwright test tests/e2e/auth/shadow-claim-with-data.spec.ts --list

The --list should enumerate the 4 journey steps (× each configured device project).

2. Run it for real — the check that counts

This spec signs a user up, so it needs the dev Supabase stack and a service-role key. See the local E2E runbook for the tunnel/port setup. Run a single project — it is a serial journey against a shared database, and running all 7 device projects concurrently will have them fight over the same seed data. 
npx playwright test tests/e2e/auth/shadow-claim-with-data.spec.ts \
  --project="Desktop Chrome"

Prerequisites the spec asserts on in beforeAll (it fails fast and clearly if these are missing):

  • a seeded non-shadow teacher profile
  • at least 2 songs in the songs table

Expected: 4 steps pass in order. Step 3 is the meaningful one — it proves the claim happened in place. Step 4 proves the student actually sees the songs and lessons in the UI, which is the outcome a user cares about.

3. Confirm it fails for the right reason (optional but worthwhile)

To check the spec is a real guard and not a test that passes regardless, temporarily point handle_new_user at a plain INSERT (no claim) on the dev stack and re-run. Step 3 should fail on profile id must survive the claim unchanged, and step 4 should show an empty repertoire. Restore the function afterwards.

Dev stack only — port 55321 (StudentDevelopment). Port 54321 is production.
