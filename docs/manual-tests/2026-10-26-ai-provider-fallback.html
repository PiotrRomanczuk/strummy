AI provider fallback: OpenRouter → Ollama → OpenAI

Date: 2026-10-26 · Branch: fix/ai-provider-fallback-chain · Scope: lib/ai, app/actions/ai, E2E runner env

What was done

  • Problem. Nightly E2E had been red since 2026-10-23. E2E was pinned to OpenAI gpt-4.1-nano, which now answers 404 model_not_found. The error was swallowed, so the assignment AI button left the brief empty, with no error and no fallback.
  • Now. With AI_PROVIDER=auto (the default, used by production) every AI request walks the chain OpenRouter → Ollama (local LLM) → OpenAI. Each provider is tried in turn, and an error is returned only when all three have failed. The error names the reason for each provider.
  • Unconfigured providers. A provider without a key, or an unreachable Ollama (2 s availability check), is skipped. On Vercel, Ollama is unreachable, so production effectively runs OpenRouter → OpenAI.
  • No splicing. A stream switches provider only before any text has been produced, so two different answers are never stitched together.
  • Model per provider. Each provider gets its own model: Ollama gets OLLAMA_DEFAULT_MODEL (default qwen3.5:9b, the model actually installed on the Windows box, with think:false). OpenAI is pinned to gpt-4o-mini.
  • Visible errors. Providers now report failures the same way (finishReason:'error' + error), and the UI shows Error: … instead of an empty field.
  • Chat. The assistant chat tries tool calling through OpenRouter first. If that fails before any text, it answers through the chain without tools.
  • Removed. AI_PREFER_LOCAL is gone, since the order is fixed. The debug panel shows "Fallback Order" instead.
  • E2E. E2E on uwh uses the same chain (AI_PROVIDER=auto). The runner sits in the LAN, so it reaches Ollama directly.
  • Env. OPENAI_API_KEY was added to Vercel Production, so production has the third rung.

How to test manually

  1. Prod after merge. On strummy.online, as a teacher, go to Assignments → New, pick a student, enter a title and click the AI button. Expected: the brief fills with text within a few seconds.
  2. Fallback locally. In .env.local, set OPENROUTER_API_KEY=sk-or-v1-invalid and OLLAMA_BASE_URL=http://192.168.1.10:11434, then npm run dev and repeat step 1. Expected: text from Ollama (the first one can take ~15 s), and the server log shows [AI Fallback] OpenRouter … — trying next provider.
  3. All down. Additionally set OLLAMA_BASE_URL=http://192.168.1.250:11434 and OPENAI_API_KEY=sk-invalid. Expected: the brief shows Error: All AI providers failed — … rather than staying empty.
  4. Nightly. Dispatch nightly-e2e.yml on main (Desktop Chrome). Expected: the @ai tests (assignment-ai, ai/feedback, lesson-notes-ai) pass.
  5. Debug panel. /dashboard/admin → AI Provider should show Fallback Order: OpenRouter → Ollama → OpenAI.

Edge cases worth a look

  • Windows box asleep: Ollama is skipped after 2 s, and the request lands on OpenAI.
  • A provider that fails mid-answer: no switch, the partial answer stays, and the error is passed through.
  • AI_PROVIDER=openrouter|ollama|openai|mock still forces a single provider, with no fallback.
