Manual test — user_id → profile_id rename

2026-07-31 · branch refactor/profile-id-column-naming · migration 20260731143000_rename_profile_fk_columns.sql

What was done

user_id meant two different things in this schema. Thirteen tables used it for auth.users.id; fourteen used it for profiles.id. Those are different UUIDs, so joining or filtering on the wrong one returns zero rows instead of an error — the failure looks like "this user has no roles", not like a bug.

After this change the rule is absolute and mechanically checkable:

Column name Always means
user_id auth.users.id
profile_id / recipient_profile_id public.profiles.id

Also renamed: the 14 FK constraint names and the 6 index names that embedded user_id (FK violation errors print the constraint name — leaving user_roles_user_id_fkey on a column called profile_id would put the ambiguity back exactly where someone reads it while debugging).

Three production bugs fixed on the way

These were found because of the rename, not incidentally. All three pass an auth id into a column that is FK'd to profiles.id.

File Was Effect in production
app/actions/admin/ai-check.ts .eq('user_id', user.id) on user_roles Admin check matched nothing → "Unauthorized: Admin access required" for any admin whose profile id ≠ auth id
app/actions/ai/shared.ts user_id: user.id insert into ai_generations FK violation on every insert, swallowed by the surrounding catch → AI generations silently never logged
lib/ai/registry/analytics.ts user_id: request.context.userId Same, for agent_execution_logs. AgentContext already carries a correct profileId field, documented for exactly this
Why these survived until now In production, 1 of 7 profiles has id == user_id — and it is the admin/owner account (created 2026-07-19, before the S2 identity split). The other six were all created 2026-07-30 and have differing ids. So every one of these paths works when the owner tests it and silently fails for all six real users.

Worse for test coverage: all three E2E role accounts (admin@dev.local, teacher@dev.local, student@dev.local) also have id == user_id, while 3,728 of 3,928 dev profiles do not. Every E2E test passes regardless of which id it uses — the suite is structurally blind to this bug class. tests/e2e/teacher/ai-history.spec.ts had the wrong model written into its header comment as if it were correct; it is fixed here.

A miss worth recording The first version of the migration recreated 6 functions but missed 4, because the detection query listed the affected tables by hand and omitted notification_log and notification_queue. It was caught by divergent-identity.rls.test.ts failing with column "recipient_user_id" of relation "notification_queue" does not exist — a profile INSERT fires tr_notify_student_welcome. That would have broken every signup in production. The migration's post-condition guard has been widened to be deliberately coarse so this cannot recur.

How to test it manually

Prerequisites

  • On the Orange LAN (dev Postgres is LAN-only)
  • Dev stack migrated — already done; re-apply is a safe no-op if unsure
  • Dev credentials: bottom of CLAUDE.md / CLAUDE.local.md

1. Confirm the schema rule holds

This should return zero rows — no FK to profiles.id is named user_id anymore: 

ssh uwh "docker exec -i supabase_db_StudentDevelopment psql -U postgres -d postgres -c \
  \"select c.conrelid::regclass, a.attname
     from pg_constraint c
     join pg_attribute a on a.attrelid=c.conrelid and a.attnum=c.conkey[1]
     where c.contype='f' and c.confrelid='public.profiles'::regclass
       and a.attname like '%user_id%';\""

And the inverse — profiles.user_id must still point at auth:

-- expect exactly one row: profiles.user_id -> auth.users.id
ssh uwh "docker exec -i supabase_db_StudentDevelopment psql -U postgres -d postgres -c \
  \"select conrelid::regclass, confrelid::regclass from pg_constraint
     where contype='f' and confrelid='auth.users'::regclass
       and conrelid='public.profiles'::regclass;\""

2. Run the app

npm run dev

Sign in as admin, then walk these. Each one reads or writes at least one renamed column:

3. Exercise the paths that were actually broken

The important one. These only prove anything with an account whose profiles.id ≠ profiles.user_id — with a matching account they pass either way. Find or make one: 

ssh uwh "docker exec -i supabase_db_StudentDevelopment psql -U postgres -d postgres -c \
  \"select email from profiles where id <> user_id and user_id is not null limit 5;\""
  1. AI generation logging — sign in as a divergent user, run any AI action, then confirm a row landed: 
    select count(*) from ai_generations
where profile_id = (select id from profiles where email = '<that email>');
    Before this change that insert raised an FK violation and was swallowed — the count stayed at 0.
  2. Admin AI status check — as an admin whose ids diverge, open the admin AI status panel. Before: "Unauthorized: Admin access required". After: it reports provider status.
  3. Signup trigger — create a new student profile and confirm a welcome row was queued (this is the path the migration miss would have broken): 
    select notification_type, recipient_profile_id, status
from notification_queue order by created_at desc limit 5;

4. Edge cases worth a look

  • Realtime notifications — useNotifications subscribes with a filter string profile_id=eq.<id>. Open two tabs, trigger a notification, confirm it appears live. A stale filter string fails silently (no error, just no updates).
  • Queue processor — get_pending_notifications is the one RPC whose output column changed. Run the queue processor and confirm items move out of pending; if the RPC contract broke, everything stays pending with no error.
  • Shadow profile claim — transfer_shadow_profile_references repoints ~30 columns. Claim a shadow profile and confirm the returned JSON counts look sane.
  • Bounce handling — notification_log.recipient_profile_id drives consecutive-bounce auto-disable. Not easily triggered by hand; covered by lib/email/__tests__/bounce-handler.test.ts.

Known gaps left deliberately

  • Tables not renamed. user_roles, user_preferences, user_history keep their names. The hazard was the column ambiguity, not the table name; renaming tables is pure churn with no correctness payoff.
  • transfer_shadow_profile_references behaviour unchanged. It repoints user_history.changed_by but not user_history.profile_id, so merging a shadow profile leaves those rows pointing at the old profile. Pre-existing; fixing it is a behaviour change and belongs in its own PR, not in a rename.
  • E2E blindness not fixed. The role accounts still have id == user_id. Making ensure-test-users-setup.ts seed divergent ids would make the whole E2E suite able to catch this class — worth doing, but it is a separate change with its own blast radius.
