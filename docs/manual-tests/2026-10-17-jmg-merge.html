What was done

  • Overlay tool: justmeandguitars-overlay-app was added at tools/chord-overlay/ with git subtree add, so its history came with it. It is a standalone Next.js app with its own package.json. Strummy's tsconfig, ESLint, Jest (testPathIgnorePatterns + modulePathIgnorePatterns), Prettier, Tailwind source detection (@source not '../tools') and the new .vercelignore all skip tools/.
  • Content plan: songs.yaml, strategy.yaml, TODO, README and the April plan/spec docs were copied to docs/marketing/tiktok/. The XLSX, venv and scripts stay in the archived repo.
  • Catalogue import: added scripts/database/seeding/import-jmg-songs.ts (with .helpers, .guard and .data modules, plus 35 unit tests in __tests__/scripts/import-jmg-songs.test.ts). It does a dry run unless you pass --apply, and --target dev|prod is required. The guard checks two things. First, the URL must be uwh's port for that target, or a localhost SSH tunnel. Second, the connected cluster's system_identifier must match the value pinned for that target. A prod run also needs --backup pointing at a dump less than 6 hours old.
  • Mapping:
    • artist → author.
    • ★ count → level: ≤2 beginner, 3 intermediate, ≥4 advanced. starter is never assigned.
    • status → priority_bucket: ✅ DONE→done, 📅 MAY→may, 📅 JUNE→june, ⏳ LATER→later, ⏳ BACKLOG→backlog. Any other status is a hard error.
    • genre → category.
    • tiktok_short_url stays NULL.
    • Shorthand titles are expanded to the real song names, e.g. "Hotel Cali Solo"→"Hotel California" and "GnR"→"Guns N' Roses".
  • Dedup and updates:
    • Songs match on normalised lower(title) + lower(author). The normaliser ignores a leading "The", text in parentheses and a trailing "solo".
    • Only active rows are matched.
    • A match updates priority_bucket. It fills level/category only when they are empty, so curated values win.
    • Any song whose URL is a fake tiktok.com/@strummyapp/video/… has that URL cleared.
    • Two YAML duplicates are collapsed, keeping the most committed bucket: Wonderwall (MAY over LATER) and Hotel California (its "Solo" entry).
  • No columns are needed for ownership: public.songs has no created_by/teacher column, and service-level Postgres access bypasses RLS.

How to test

1. Strummy is unaffected by tools/

npm ci
npm run lint && npm run typecheck && npm test && npm run build

Expected: all green, and nothing under tools/ appears in the lint, typecheck or test output.

2. The overlay tool still runs on its own

cd tools/chord-overlay && npm install && npm run dev   # needs ffmpeg for baking

3. Mapping unit tests

npx jest __tests__/scripts/import-jmg-songs.test.ts   # 35 tests

4. DEV import (Mac on the home LAN)

macOS blocks Node from LAN sockets in some shells (EHOSTUNREACH), so go through an SSH tunnel:

ssh -f -N -L 55322:127.0.0.1:55322 uwh
export JMG_IMPORT_DB_URL="$(grep '^POSTGRES_URL=' .env.local | cut -d= -f2- | tr -d '"' | sed 's#@192.168.1.75:55322#@127.0.0.1:55322#')"
npx tsx scripts/database/seeding/import-jmg-songs.ts --target dev            # dry run
npx tsx scripts/database/seeding/import-jmg-songs.ts --target dev --apply    # write

Expected: Cluster identity verified: DEV, and re-running it plans 0 changes. In the UI (dev server, teacher account), go to Songs and search "Fast Car", "Jolene" or "Comfortably Numb": each should exist with its level. "Hotel California" should still be advanced.

5. The guard refuses the wrong target

JMG_IMPORT_DB_URL=postgresql://x:y@192.168.1.75:54322/postgres npx tsx scripts/database/seeding/import-jmg-songs.ts --target dev
# ❌ Refusing: --target dev expects 192.168.1.75:55322 … got 192.168.1.75:54322
npx tsx scripts/database/seeding/import-jmg-songs.ts --target prod --backup some.dump   # over the DEV tunnel
# ❌ Refusing: connected cluster is DEV, not PROD

Later: PRODUCTION import (manual, separate step)

Warning: ~/bin/strummy-prod-backup.sh on uwh has CONTAINER="supabase_db_StudentDevelopment". As of 2026-10-17 the nightly "prod" backup on the NAS is a dump of DEV, so do not rely on it. Take the dump below by hand, and get the backup script fixed separately.
  1. Take a fresh full dump of StudentProduction and check it: 
    D=strummy-prod-pre-jmg-$(date +%F-%H%M).dump
ssh uwh 'docker exec supabase_db_StudentProduction pg_dump -U supabase_admin -Fc -d postgres' > "$D"
ls -lh "$D"                                    # expect tens of MB, never a few KB
ssh uwh 'docker exec -i supabase_db_StudentProduction pg_restore -l' < "$D" | head   # TOC lists OK
    Copy it to the NAS as well (Backups/strummy-prod/).
  2. Open a tunnel to prod Postgres and set the URL. The password comes from the password manager or CLAUDE.local.md, never from this repo: 
    ssh -f -N -L 54322:127.0.0.1:54322 uwh
export JMG_IMPORT_DB_URL='postgresql://postgres:<prod-password>@127.0.0.1:54322/postgres'
  3. Dry run, and read every line: 
    npx tsx scripts/database/seeding/import-jmg-songs.ts --target prod --backup "$D"
    Expect Cluster identity verified: PROD (7654158243728179239), roughly 40–58 inserts, and placeholder clears only where prod actually has fake URLs.
  4. Apply: run the same command with --apply. Check that the "After" active-song count equals "Before" plus the number of inserts.
  5. Check that https://strummy.online returns 200, that the Songs list shows the new songs, and that ssh uwh 'docker ps | grep -c StudentProduction' shows all containers Up.
  6. Rollback if needed: the import touches only public.songs. Restore that table from "$D" (pg_restore -t songs --data-only into a scratch DB, then copy over), or delete the inserted rows by title and author.
