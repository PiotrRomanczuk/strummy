Students can pick a song to learn

2026-07-31 · branch feature/student-want-to-learn · migration + 2 RPCs + UI

What was actually done

A student browsing the song library can now mark any song "Want to learn". It lands in their repertoire at the to_learn stage and the teacher sees it, badged "Student picked", on the student-detail Repertoire tab.

Before this, students had no write path into student_repertoire at all — RLS granted INSERT to admins and teachers only, and the song page literally told them to "ask your teacher to add it".

Students still get no direct INSERT/DELETE policy. Both writes go through SECURITY DEFINER RPCs scoped to current_profile_id(), the same shape as the existing set_assignment_status. That matters because RLS gates rows, not columns: a bare INSERT policy would have let a student set teacher_notes, priority, or open a song straight at mastered. The RPC decides those.

Where the control appears

Surface What the student sees
Song detail → "Your practice" card Want to learn when the song is not in their repertoire; Remove while the pick is still untouched; the stage stepper with no button once it is teacher-assigned, started, or practised.
Song library rows (/dashboard/songs) A compact Want to learn per row; rows already in the repertoire read In your repertoire. Undo lives on the song page, which is the only surface that knows whether the entry is still removable.
Teacher → student detail → Repertoire A Student picked badge next to the song author on rows the student chose themselves.

What a student may and may not do

Action Allowed Why
Add any library song yes Idempotent — re-marking returns the existing entry rather than erroring.
Remove their own untouched pick yes Mis-taps stay recoverable.
Remove a teacher-assigned song no A student must not be able to delete assigned work.
Remove after the status moved past to_learn no The row now represents real progress, possibly with lessons built around it.
Remove after logging any practice no Same — history is not erasable through this path.
Add a deleted / unknown song no Checked explicitly, not left to the FK: the FK would accept a soft-deleted song, which would then render as a blank repertoire row.
Set status / notes / priority when adding no The RPC pins the new row to to_learn and the caller's own profile.

Two bugs found and fixed on the way

1. A pre-existing bug that sat directly in this feature's path

getSongLearners filters .neq('current_status', 'to_learn') — correct for the teacher's "who is learning this" list. But the student's own progress card was reading its state from that same query. Since a "want to learn" pick is a to_learn row, the card would have come back empty and told the student the song was not in their repertoire, immediately after they pressed the button. Fixed by giving the viewer their own query, getViewerSongEntry. Journey W2 in the E2E spec guards it.

2. A bug the automated gates could not see

canStudentRemove was first written as a synchronous export from app/actions/repertoire.ts, which carries 'use server'. Next.js requires every export from a server-action module to be async, so this failed at bundle time with "Server Actions must be async functions" and returned HTTP 500 on /dashboard/songs, the song detail page, and /dashboard/repertoire. npm run typecheck and all 293 Jest suites passed the whole time — only the Next bundler enforces that rule, so only actually loading a page caught it. The helper now lives in lib/services/repertoire.helpers.ts and is shared by the action and the query layer.

How to test it manually

Setup

cd ~/Desktop/MainCV/strummy
git checkout feature/student-want-to-learn
npm run dev

The migration is already applied to the StudentDevelopment stack on uwh. Sign in with email/password using the dev role accounts from CLAUDE.local.md — Google SSO does not work against a LAN dev stack.

1 — Pick a song from the library (student)

  1. Sign in as Student, go to Song Library.
  2. expect each row has a small Want to learn on the right. Rows already in your repertoire read In your repertoire instead.
  3. Click Want to learn on a row. It should show Saving… briefly, then settle. Clicking the row itself must still navigate to the song — the row is a stretched link with the button layered above it, so check both behaviours.
  4. Go to My Repertoire. The song is there at the "To learn" stage.

2 — Pick and un-pick from the song page

  1. Open a song that is not in your repertoire.
  2. expect the "Your practice" card reads "Not in your repertoire yet — add it and your teacher will see it" with a Want to learn button.
  3. Click it. The card should switch to the stage stepper plus a Remove button. Reload the page — it must still show as in your repertoire. (Reloading is the important step: this is exactly where bug #1 above would have shown up.)
  4. Click Remove. The card returns to the un-picked state.

3 — The guard rails (the part worth testing properly)

  1. As a teacher, assign a song to that student from their student-detail Repertoire tab.
  2. Back as the student, open that song. expect no Remove button and no Want to learn button — just the stage stepper. A student must not be able to delete work their teacher assigned.
  3. Take one of your own picks and log a practice session against it (or have the teacher move it to "Started"). Reopen the song — expect the Remove button is now gone.
  4. Double-click Want to learn quickly. Only one row should be created, and no error should appear — the write is idempotent.

4 — Teacher's view of the request

  1. As Teacher, open that student → Repertoire tab.
  2. expect a Student picked badge beside the author on rows the student chose. Songs you assigned carry no badge.

5 — Edge cases worth a look

  • Parents also see the "Your practice" card. They should get the original "ask your teacher to add it" wording and no button — they are not the learner.
  • Teachers/admins see the Usage + Learners cards instead, unchanged.
  • Mobile (≤ 640px): the library grid collapses to one column. Check the action does not overlap the meta line, and that row-tap still navigates.
  • Demo accounts (is_development: true) are blocked by guardTestAccountMutation and should get a refusal, not a crash.

canStudentRemove mirrors the SQL predicate so the UI never offers a button the database would refuse. Its unit tests assert one clause per test, so if the two ever drift the failure names which clause moved. The RPC remains the authority — the client cannot talk it into deleting a protected row, which journey W4 proves against the real DB.

Migration

supabase/migrations/20260731120000_student_want_to_learn.sql — applied to StudentDevelopment, and database.types.ts regenerated from the live dev schema (clean additive diff: one column, two RPCs).

  • Adds student_repertoire.added_by_student boolean not null default false. An explicit column rather than reusing assigned_by, which is documented as "Teacher who added this song" — self-assignment there would break every query joining it to a teacher.
  • add_song_to_my_repertoire(uuid) and remove_song_from_my_repertoire(uuid), both SECURITY DEFINER, granted to authenticated.
  • Idempotent DDL throughout, so re-applying is safe.

Not yet applied to production. Merging to main deploys straight to strummy.online, and the app expects added_by_student to exist — apply the migration to StudentProduction before merging, or the repertoire queries will fail with Postgres 42703.
