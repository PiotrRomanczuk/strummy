Least privilege for baseline objects

2026-11-25 · migration 20261125190000_least_privilege_baseline_objects.sql · backend only, no UI change

What was done

The baseline schema gave the anon and authenticated roles every right on every view and EXECUTE on every function. Tables are protected by RLS, but views that run with their owner's rights and SECURITY DEFINER functions are not, so for them the grant is the only protection. This migration narrows it:

Object Before After
user_overview owner's rights, open to anon and signed-in users security_invoker, no anon/authenticated grants (the app does not use it)
lesson_counts_per_student, lesson_counts_per_teacher, song_usage_stats, mv_song_engagement, mv_song_popularity open to anon and signed-in users service role and postgres only (unused by the app)
9 maintenance / notification functions (get_pending_notifications, mark_overdue_assignments, refresh_song_engagement, cleanup_*, get_bounce_stats, get_*_email_count_last_hour, soft_delete_song) EXECUTE for everyone service role (and pg_cron as supabase_admin) only — the only real callers
soft_delete_song_with_cascade EXECUTE for everyone, no caller check signed-in users and service role; a signed-in caller must be teacher or admin (same rule as songs_update_staff)
lesson_history SELECT policy every signed-in user whoever can see the lesson (policy delegates to the lessons policies)

migrate-db.sh classify → additive: it applies on every branch database without the production-db approval.

Automated tests added

  • lib/testing/rls/__tests__/baseline-grants.rls.test.ts — 24 cases: user_overview read/write refused for anon and a student; each service-only function refused for anon and a student, still served to the service role; song deletion refused for anon and a student, allowed for a teacher.
  • lib/testing/rls/__tests__/lesson-history.rls.test.ts — 5 cases: the lesson's teacher and student see a history row; another teacher, another teacher's student and anon do not.

How to test manually

  1. Classify and run the suites (dev stack configured in .env.local): 
    bash scripts/e2e-remote/migrate-db.sh classify supabase/migrations/20261125190000_least_privilege_baseline_objects.sql
npx jest --config jest.config.rls.ts lib/testing/rls/__tests__/baseline-grants.rls.test.ts lib/testing/rls/__tests__/lesson-history.rls.test.ts
    Expect additive and 29 passed.
  2. From outside the app, with only the public key: 
    curl -s -o /dev/null -w "%{http_code}\n" "$NEXT_PUBLIC_SUPABASE_LOCAL_URL/rest/v1/user_overview?select=user_id&limit=1" \
  -H "apikey: $NEXT_PUBLIC_SUPABASE_LOCAL_ANON_KEY"
    Expect 401.
  3. As a teacher in the app: delete a song with no active lesson from Songs. Expect it to disappear from the list (deletion still works for staff).
  4. As a teacher: open a lesson you edited (/dashboard/lessons/<id>). Expect the change history to be listed as before.
  5. After the next cron run on dev: notification queue, bounce check and e-mail rate limits keep working (they use the service role) — check Logs for errors from get_pending_notifications or get_bounce_stats.
