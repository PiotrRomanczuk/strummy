Security gates before inviting a student

2026-11-15 · branch sprint/security-gates · no browser session was used, so there are no screenshots; every scenario below is a database or HTTP-level check.

What was done

A — profiles. Until now any signed-in user could send PATCH /rest/v1/profiles?user_id=eq.<own uid> with {"is_admin": true} and become an admin, because profiles_update_own restricted the row but not the columns. A new BEFORE UPDATE trigger (profiles_guard_self_update, migration 20261115120000_profiles_guard_self_update.sql) lets a non-admin change only full_name, first_name, last_name, phone, avatar_url, locale, updated_at; anything else fails with SQLSTATE 42501 and the whole UPDATE is rolled back. Admins, service_role, postgres and SECURITY DEFINER functions are not restricted. The list is an allow list, so a column added later is protected by default. The migration is additive (migrate-db.sh classify → additive) and does not depend on the dev/prod drift.

B — Cal.com webhook. POST /api/webhooks/calcom now fails closed:

  • no CALCOM_WEBHOOK_SECRET → 500 and an error log, nothing is processed (before: every request was accepted);
  • signature compared with crypto.timingSafeEqual on equal-length buffers; missing, non-hex or wrong-length signature → 401 without an exception;
  • only BOOKING_CREATED creates a lesson; other events → 200 {"ignored": "<event>"};
  • the attendee e-mail is validated (Zod) and looked up with two .eq() filters instead of being interpolated into .or(); an invalid address (comma, bracket, whitespace) → 400;
  • 500 responses carry a fixed message; the internal error stays in the log.

Out of scope (separate tasks): sr_update_own_notes, constant-time compare in cron/Google webhooks, duplicate policies, teacher self-signup.

Edge cases and caveats

  • Every write to profiles done by the app with the user's own session must stay within the allow list. Checked: app/actions/profile-settings.ts and app/api/users/profile/route.ts write only allowed fields; onboarding, account deletion, lockout and Cal.com intake use the admin client; the three PL/pgSQL functions that update profiles are SECURITY DEFINER.
  • is_admin() reads the committed row, so one UPDATE cannot both grant and use the flag.
  • The Cal.com secret has to be set on Vercel before merge, otherwise real bookings get 500 until it is. Rotate the secret afterwards.
  • db-parity / types-drift may be red because of the existing dev/prod drift, not because of this change (the trigger changes no column and no generated type).
