Lessons only with own students

Date: 2026-11-25 · Branch: fix/lesson-own-students (stacked on chore/lesson-assignment-tests-real-db, PR #1196) · Decision: owner, 2026-11-25 · Checked on: Mac on the home LAN against StrummyDevelopment, migration applied there.

What was done

Part Change
Rule A teacher gives a lesson to a student they already teach (a non-deleted lesson together), or to a student nobody teaches yet (a new student's first lesson). An admin is not restricted.
Migration 20261125200000_lessons_own_students.sql New public.may_teach_student(uuid) (SECURITY DEFINER, executable by authenticated and service_role only). The lessons_insert_teacher policy and the WITH CHECK of lessons_update_teacher call it. That covers every teacher-side path that writes lessons with the caller's client: the lesson form, /api/lessons, bulk, schedule and recurring. Classified additive by migrate-db.sh classify.
createLessonAction When the policy refuses the insert, the form gets "You can only schedule lessons with your own students" instead of the raw RLS message.
Types database.types.ts regenerated from dev (npm run db:types) for the new function.

Tests (real dev database)

  • lessons.rls.test.ts: a direct insert for another teacher's student is refused (42501). Moving an own lesson to that student is refused, and the lesson keeps its student. A further lesson for an own student and a first lesson for a new student both work.
  • lesson-edit.rls.test.ts: the form refuses another teacher's student, whether picked by id or typed by email, and writes nothing. A new student's email still creates a shadow profile and the first lesson (intake unchanged).
  • Before the migration was applied, exactly the four "refused" tests failed and the intake test passed. With the migration applied, all pass.

How to test manually

  1. Apply the migration to the dev stack, if deploy-db.yml has not done it yet: 
    ssh elite 'docker exec -i supabase_db_StrummyDevelopment psql -U postgres -d postgres' < supabase/migrations/20261125200000_lessons_own_students.sql
  2. Run the suites: 
    npx jest -c jest.config.rls.ts lib/testing/rls/__tests__/lessons.rls.test.ts app/actions/__tests__/lesson-edit.rls.test.ts
    Expected: all pass.
  3. In the app (dev, teacher account): create a lesson with a student from the picker. It works as before, because the picker lists only your own students. Type the email of a brand-new student: a shadow student and the lesson are created. Type the email of a student who has lessons only with another teacher: the form shows "You can only schedule lessons with your own students".
  4. As admin: creating a lesson for any student still works.

Results (2026-11-25)

  • Dry run of the migration in a rolled-back transaction on dev: both policies recreated with the new check. Then applied for real.
  • RLS suites: see the PR description for counts. Gates: lint, typecheck, unit with coverage, structure check.

Limits

  • Service-role writers (calendar import, Cal.com webhook, transcript drafts) bypass RLS by design and are not limited by this policy.
  • Two teachers can still share a student when the second one got the student first through admin or service-role paths. The rule stops a teacher from taking over; it does not split existing pairs.
