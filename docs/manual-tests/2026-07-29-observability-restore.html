Observability restore — manual test guide

2026-07-29 · branch fix/observability-restore-sentry-and-crons · Strummy v0.160.0

What was wrong

An audit of the monitoring/logging stack found the architecture sound but the two things that would actually tell you production is broken switched off, and the third quietly corrupting its most useful field.

Problem Effect in production
NEXT_PUBLIC_SENTRY_DSN never set in Vercel Sentry initialised as a silent no-op. Every logger.error, every error boundary, every cron monitor reported nowhere.
90 of 551 logger.error call sites pass { error } as the error arg Persisted to system_logs as message: "[object Object]" with a null context — the admin log viewer showed nothing usable.
cleanup-auth-events dropped when crons collapsed into the dispatcher (3d2f1c25, Jul 23) GDPR 90-day deletion of auth_events (emails + IPs) had not run since.
CRON_REGISTRY advertised 11 per-route schedules that no longer exist Debug dashboard claimed the notification queue ran every 15 min; it runs daily.
system_logs had no retention Unbounded growth on the self-hosted prod Postgres.
Dispatcher counted { success: false } bodies as successes Cron routes return 200-with-error-payload by design, so a job could fail every day and log nothing.
tracesSampleRate: 1 + enableLogs: true on all runtimes Would have burned the Sentry quota the moment a DSN was set.

What changed

  • Logger tolerates the wrapper shape. New lib/logger/normalize-error.ts unwraps { error, ...context } in the error position, so all 90 call sites now persist real messages and stacks — and the 91st can't regress. Amendment recorded in ADR 0003. serializeError JSON-stringifies message-less objects as a backstop.
  • Sentry tuned for a live DSN: sampling 1 → 0.1 (env-overridable), enableLogs off (warn/error already land in system_logs), environment + release tagging added, AI SDK prompt/completion recording turned off (student names and lesson notes were being sent).
  • /monitoring excluded from the middleware matcher — otherwise the Sentry tunnel redirects logged-out users to sign-in and their error reports vanish.
  • Two jobs restored/added to the dispatcher: cleanup-auth-events (GDPR) and a new prune-system-logs (warn 30d, error 90d).
  • Dispatcher detects reported failures — a { success: false } body now logs an error and counts as failed; { skipped: true } stays a no-op.
  • CRON_REGISTRY tells the truth — every entry carries a trigger (vercel-cron / via-dispatcher / manual) and the dispatcher's real cadence; the debug panel renders it.
Prerequisite — two values only you can set. Everything below except §1 works without them; §1 is the whole point of the change. 
npx vercel env add NEXT_PUBLIC_SENTRY_DSN production
# sentry.io → org bmr-p0 → project guitar-crm → Settings → Client Keys

npx vercel env add SENTRY_AUTH_TOKEN production
# sentry.io → Settings → Auth Tokens, scope: project:releases
# (build-time only — uploads source maps so stack traces aren't minified)
Redeploy after adding them: NEXT_PUBLIC_* is inlined at build time, so an existing deployment will not pick the DSN up.

How to test

1. Sentry actually receives errors

  1. Set both env vars above, redeploy, then open the preview/production app and visit a route that throws. Easiest deliberate trigger: sign in as admin and hit an API route with a malformed payload, or temporarily add a throw new Error('sentry smoke test') to a server action.
  2. Expect: the event appears in Sentry within ~30s, tagged environment: production (or preview), with a readable stack trace pointing at real filenames — not minified chunk-abc123.js frames. Minified frames mean SENTRY_AUTH_TOKEN was missing at build time.
  3. Confirm the tunnel works for logged-out users: open the app in a private window (signed out), trigger a client error from the console (setTimeout(() => { throw new Error('anon test') })), and check it arrives.
    Expect: a POST to /monitoring returning 2xx in the network tab, and the event in Sentry. /monitoring currently 404s in production (verified 2026-07-29) because the tunnel route isn't emitted without a DSN at build time — it should start existing after the redeploy.

    Note: the middleware's auth redirect is scoped to /dashboard, so /monitoring was never being redirected and reports were not being dropped by it. Excluding it from the matcher follows Sentry's guidance and saves a pointless getUser() round-trip per error POST — it is not a bug fix.

2. The admin log viewer shows real errors (the [object Object] fix)

  1. Sign in as admin and open /dashboard/logs.
  2. Trigger a failure that goes through one of the wrapper-shaped call sites — e.g. edit a lesson so the insert violates a constraint (app/actions/lesson-edit.ts:79 logs { error }), or delete a song still referenced by a repertoire row.
  3. Expect: the new row's details show the actual Postgres message (e.g. duplicate key value violates unique constraint …) plus any sibling context fields such as studentId. Not Error: [object Object], which is what every one of these rendered as before.
  4. Filter by level=error and skim the existing rows. Old rows written before this deploy will still read [object Object] — that data is already lost. Only rows created after the deploy are fixed.

3. Cron fleet — dispatcher runs the restored jobs

  1. Invoke the dispatcher by hand against preview (needs CRON_SECRET): 
    curl -s -H "authorization: Bearer $CRON_SECRET" \
  https://strummy-preview.vercel.app/api/cron/dispatcher | jq '.summary, .jobs[].name'
  2. Expect: summary.total is 11 on a weekday (12 on Sunday or Monday), and the job list includes cleanup-auth-events and prune-system-logs. Before this change it was 9 and neither was present.
  3. Run the prune route alone and check the tiers: 
    curl -s -H "authorization: Bearer $CRON_SECRET" \
  https://strummy-preview.vercel.app/api/cron/prune-system-logs | jq
    Expect: warn.retentionDays: 30, error.retentionDays: 90, and a deletedCount. On a fresh DB without the table it returns skipped: true with HTTP 200 — that is the designed graceful path, not a failure.
  4. Verify the GDPR job really deletes. On uwh, before and after a dispatcher run: 
    ssh uwh "docker exec -i supabase_db_StudentProduction psql -U postgres -d postgres \
  -c \"select count(*), min(occurred_at) from public.auth_events;\""
    Expect: after the run, min(occurred_at) is no older than 90 days. If rows older than that survive, the job did not reach the DB.

4. Cron failures are no longer reported as successes

  1. Simplest check is the unit test, which encodes the exact regression: 
    npx jest __tests__/app/api/cron/dispatcher.test.ts
  2. In the app: temporarily break one job's dependency (e.g. unset GMAIL_APP_PASSWORD on preview so the reminder job returns { success: false }), then run the dispatcher.
    Expect: summary.failed >= 1, the job's entry has status: "error" with the reported reason, and a matching row appears in /dashboard/logs (and in Sentry once the DSN is live). Previously this returned failed: 0 and logged nothing.

5. Debug dashboard stops advertising fictional schedules

  1. Sign in as admin, open /dashboard/admin/debug, find the Cron Jobs card.
  2. Expect: 15 jobs. Exactly one — the dispatcher — is badged vercel cron; every other is badged via dispatcher and shows 0 6 * * * (weekly jobs show their day). No entry claims */15 * * * * any more.

6. Nothing regressed

npm run lint        # 0 errors (298 pre-existing warnings, none in changed files)
npm run typecheck   # clean
npm test            # 289 suites, 3792 passed, 5 skipped

New coverage: lib/__tests__/normalize-error.test.ts (26 cases, including a regression guard asserting a persisted row is never [object Object]) and __tests__/app/api/cron/prune-system-logs.test.ts (5 cases).

Known gaps left open

  • No unauthenticated liveness endpoint. /api/health is admin-gated, so Uptime Kuma on the Pi still can't probe the app and a whole-app outage is detected manually. A /api/ping returning 200 + build SHA would close it.
  • Whole-dispatcher failure is still silent. Per-job failures now log, but nobody reads the dispatcher's own response — a timeout or cold-start crash reports nowhere. Needs an external prober or a home-ops ingest emit.
  • lib/logging/notification-logger.ts is still a parallel stack. 420 lines, 9 importers, raw console.*, its own Sentry path gated on a different (also unset) SENTRY_DSN variable. Nothing it logs reaches system_logs. Deliberately deferred.
  • home-ops-log.mjs is vendored but inert — one call site, INGEST_URL/INGEST_TOKEN unset in Vercel. Wire it or drop it.
  • system_logs is still missing from generated types, so two files carry any double-casts. Needs a supabase gen types run.
