Backend changes: what merging test → main does to production's schema

Date: 2026-11-19 · Branch: feature/review-backend-changes (stacked on #1128) · Scope: scripts/review/schema-inventory.sql, schema-diff.mjs, backend-changes.mjs, run-backend-changes.sh, .github/workflows/review-backend.yml. No browser was used — CLI and SQL only, so no screenshots.

What was done

  • Inventory (schema-inventory.sql): one line per object of the public schema — tables (with RLS on/off), columns (type, null, default), functions (definition hash, security definer), triggers, RLS policies, indexes, constraints, enum types, views. Catalog queries only; run on production and StrummyTest.
  • Diff (schema-diff.mjs): by (kind, name). A CHECK the server deparses two ways (::character varying casts) counts as the same — the rule of normalize() in schema-dump.lib.sh.
  • In words (backend-changes.mjs): new / changed / dropped, in Polish; a new table is one line with its column and policy counts, its policies and triggers spelled out with their rule; the migrations main lacks with migrate-db.sh classify's verdict.
  • Two honesty checks: schemas differ but no migration to explain it → a warning that StrummyTest is ahead of its branch; an object none of the listed migrations names → "⚠ żadna migracja z listy go nie wymienia".
  • Workflow review-backend.yml: same triggers as the gallery, light runner; files the backend section on the PR's review page and prints it on the run's summary page.
  • Fixed in #1128 on the way: run-review.sh resolved main as origin/main, which a shallow one-ref checkout (the workflow's) does not have; both scripts now use FETCH_HEAD, like db-parity.
