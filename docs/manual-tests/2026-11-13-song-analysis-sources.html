What was done

  • Migration 20261113140000_song_analysis_sources.sql (additive): table song_analysis_sources — one row per song and source (chord-id, chord-compare, later study), the source's document kept whole in payload. Staff read (is_admin_or_teacher()), only the service role writes — same as song_analyses.
  • schemas/SongChordReviewSchema.ts: the shape of a song2logic chord review, shared by the loader now and the app in SNG-8.
  • Loader scripts/backfill/2026-11-song-analysis-sources.ts (pure rules in song-analysis-sources-core.ts): reads a song2logic chord-review run, validates every review against the schema, upserts the review and the Chord ID result it used. It never writes to songs.
  • Blueprint: song_analysis_sources in doc 03, SNG-8 brief, roadmap thread 6D.

How to test manually

  1. On a dev database without the table: apply the migration (docker exec -i supabase_db_StrummyDevelopment psql -U postgres -d postgres < supabase/migrations/20261113140000_song_analysis_sources.sql on uwh); re-apply it — no error (idempotent).
  2. npx tsx scripts/backfill/2026-11-song-analysis-sources.ts --dir <run> --validateOnly → counts as above, problems: [], nothing written.
  3. Same with --commit and no --remote → refused ("Refusing to write … without --remote").
  4. With --commit --remote → select source, count(*) from song_analysis_sources group by 1 = 468 chord-compare, 54 chord-id.
  5. Break one review ("status": "maybe" in sources/chord-compare/<id>.json) → --validateOnly lists it under problems and counts it as invalid; nothing is loaded for that song.
  6. RLS: in one transaction on dev, set_config('request.jwt.claims', '{"sub": "<student profile id>", "role": "authenticated"}', true), set local role authenticated, select count(*) from song_analysis_sources → 0; with a teacher's id → all rows; rollback.
