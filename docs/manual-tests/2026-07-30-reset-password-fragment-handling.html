Password-reset links no longer die with "Auth session missing!"

2026-07-30 · branch fix/reset-password-fragment

What was wrong

A recovery link initiated outside the app's own /forgot-password form (e.g. a link generated via the Auth admin API) would land on /reset-password and immediately fail with "Auth session missing!" the moment the user submitted a new password — before they had even seen anything was wrong.

GoTrue hands the session over in the URL fragment (#access_token=…&refresh_token=…&type=recovery) for any link not initiated with a PKCE challenge. Fragments never reach the server, so /auth/callback's exchangeCodeForSession(?code=…) can't see them — the page has to read window.location.hash client-side. ResetPasswordForm never did; it called updateUser({ password }) on a client with no session at all.

AcceptInvitationForm (the invite-accept page) already did this correctly — PR #514 fixed it there in 2026-06-22. Reset-password was simply never given the same fix, and the app's own /forgot-password path (server action → PKCE → ?code= → /auth/callback → cookie session) never exercises the fragment path, so nothing caught the gap.

What changed

  • components/auth/useAuthHashSession.ts — new shared hook. Both pages now call the same implementation instead of two independent copies (which is how they drifted the first time).
  • ResetPasswordForm.tsx now consumes it, gated to type=recovery, and renders an actionable error panel (ResetPasswordForm.LinkError.tsx) instead of a dead form when the link is expired/invalid.
  • AcceptInvitationForm.tsx refactored onto the same hook (type=invite) — behaviour preserved, ~60 fewer lines.
A bug the live test caught that the unit tests couldn't: the first version read window.location.hash inside a useEffect. AuthHashErrorBanner (mounted in the root layout) reads and clears error hashes independently, and effect order between the two is not guaranteed — whichever ran second saw an empty hash. Fixed by capturing the hash during the initial render (useState(() => window.location.hash)), before any effect can run. Only surfaced by loading the real page in a browser with a real GoTrue error redirect; the mocked unit tests never touch the actual hash timing.

Verified against the real dev stack

Not just mocked unit tests: signed a throwaway user into StudentDevelopment for genuine GoTrue tokens, loaded the actual Next.js page in a real browser (Playwright, not jsdom), and drove three scenarios end-to-end.

Scenario Result
Real type=recovery fragment → session established, form shown, tokens stripped from the URL pass
New password submitted with that session → GoTrue accepts it, old password stops working pass
"Auth session missing!" (the original bug) not shown
Expired-link error fragment → precise "link has expired" message + "Request a new reset link" pass
No fragment, no cookie session → generic "invalid or already used" message pass
Throwaway probe user deleted via the Auth admin API during cleanup 200 (relies on PR #574's audit-trigger fix)

How to test it yourself

1. Automated

npx jest components/auth/ResetPasswordForm.test.tsx components/auth/AcceptInvitationForm.test.tsx

20 + 6 tests. The Reset suite covers fragment establish / strip / wrong-type-ignored / expired / no-session / exchange-failure. The Accept suite is new — that page had zero coverage despite being the only working implementation of this pattern before today.

2. By hand, against dev

  1. Sign in as any dev user via the token endpoint to get real access_token/refresh_token values (or trigger /forgot-password for student@dev.local and use Mailpit to grab the real emailed link).
  2. Visit /reset-password#access_token=…&refresh_token=…&type=recovery directly. The form should appear immediately, the address bar should lose the token once it settles, and setting a new password should redirect to the dashboard — no "Auth session missing!" anywhere.
  3. Visit /reset-password#error=access_denied&error_code=otp_expired&error_description=... and confirm the expired-link message replaces the form entirely (not just an inline warning next to a still-fillable form).

3. Through the UI

Request a reset from /forgot-password, click the emailed link, set a new password, sign in with it. This exercises the PKCE path, which was never broken — confirming the fix didn't regress the path real users take today.

Not covered by this change

Nothing in the app currently sends an admin-initiated recovery link (only resetPasswordForEmail via the user's own /forgot-password request, which is PKCE). This fix matters the moment anyone adds an admin "send password reset" action, or for any script/tool that calls the Auth admin API directly — which is exactly how this bug was originally found.
