Bugs found

FIXED — was High, teacher-facing, fully broken

AI Chat was completely non-functional for the Teacher role

Navigating to AI Chat loaded fine, but sending any message returned a raw Postgres error rendered directly in the chat bubble instead of a response:

new row violates row-level security policy for table "ai_conversations"

Impact: (1) the feature was 100% broken — no message could ever succeed while this RLS gap existed, and (2) a raw database error was leaking to the end user, which was also a minor information-disclosure issue (revealed table names / RLS internals). Reproduced with a plain, benign prompt ("Suggest a beginner song in the key of G.") — failed immediately, no retry helped.

Root cause (confirmed, not just "likely"): createConversation() and trackAIUsage() in app/actions/ai-conversations.ts were inserting user_id using the Supabase auth user id (supabase.auth.getUser().data.user.id), but ai_conversations.user_id / ai_usage_stats.user_id are profiles.id foreign keys, and their RLS insert policies check the row against current_profile_id() — which resolves profiles.id, never auth.uid(). Those two ids are never equal, so every teacher account hit this, not just fresh test accounts.

Fixed same day on branch fix/ai-conversations-profile-id-rls (PR #594, merged to main/staging). Both functions now reuse the profileId already resolved by getUserWithRolesSSR() — the same fix pattern already documented inline in practice.ts for practice_sessions.student_id. Added 3 regression-guard test assertions so a revert back to the auth id fails in CI. Full write-up: docs/manual-tests/2026-07-30-ai-chat-rls-fix.html.

Not yet done: live verification against a running app. PR #594 has merged to main (staging), but this was only unit-tested before merge — verify by signing in to staging and sending a real AI Chat message, then repeat once a main→production release ships it to strummy.online.
