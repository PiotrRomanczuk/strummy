Password reset link ends in the new-password form (#1177) — manual test

Date: 2026-11-24 · Branch: fix/password-reset-link → dev · Closes #1177 · verified against the development stack (mail captured by Mailpit, never sent).

What was wrong

The reset mail's link led to the marketing home page as /?code=…: no form, no message. The app asked the auth server to come back to /auth/callback?next=/reset-password. The auth server matches allowed return addresses exactly, so an address with a query string was refused and it fell back to its default site URL. The home page ignores the code.

What changed

  • app/auth/actions.ts: the reset asks to return to plain /auth/callback (allowed everywhere sign-up confirmation works).
  • app/auth/callback/route.ts + lib/auth/recovery-session.ts: a session that GoTrue issued from a reset link (its token's amr says recovery) goes to /reset-password, also for accounts without a role yet. Every other sign-in goes where it asked to (updated 2026-11-26: this replaced a one-hour "reset requested" cookie, which also caught OAuth and sign-up callbacks in that hour).
  • proxy.ts + lib/auth/stray-auth-code.ts: a stray /?code=<uuid> on the home page is forwarded to /auth/callback, so the user sees the sign-in result or the auth-error page instead of nothing.
  • messages/en.json, messages/pl.json: the "check your inbox" step no longer names a button called "Reset password".
  • tests/flows/f01-account.spec.ts: new F01.3b follows the mailed link to a new password and signs in with it (own throw-away account). It reads the PKCE code from GoTrue's redirect and opens this app's /auth/callback without next: the dev stack's GoTrue allows only localhost:3000 and redirects anything else to its site URL, while the runner serves the app on port 3200 (2026-11-26: following the link in the browser failed there with ERR_CONNECTION_REFUSED; reproduced on the Mac with the app on 3200, fixed the same way, all 6 F01 steps pass).

2026-11-26: redirect scheme after the callback

On the CI runner F01.3b then failed with ERR_SSL_PROTOCOL_ERROR: the runner serves a production build with next start over plain http, Next sets x-forwarded-host there too, and the callback built its redirect as https://<forwarded host>. The callback now takes the scheme from x-forwarded-proto (https unless it says http). Checked on the Mac the way the runner does it: npm run build, next start -p 3300, E2E_PORT=3300 npx playwright test --config=playwright.remote.config.ts tests/flows/f01-account.spec.ts → 6 passed. On Vercel the header is https, so production redirects are unchanged.

How to test manually

  1. Open /forgot-password, enter an account's e-mail, send.
  2. Open the mail in the same browser and click the link.
  3. Expect the new-password form at /reset-password; set a password; expect the success message and then the dashboard.
  4. Sign out and sign in with the new password.
  5. Open /?code=5b1f0c7e-2d34-4c8a-9a51-0e6f3b7d1a22 in a fresh browser: expect the auth-error page with instructions, not the home page.
