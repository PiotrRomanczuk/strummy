Nightly E2E z timerów na uwh

2026-11-16 · gałąź chore/nightly-e2e-timer · bez zmian w aplikacji i w bazie

Co się zmieniło

Pełny zestaw E2E na bazie dev uruchamiał GitHub czterema cronami. Pomiar z ostatnich dwóch tygodni: każdy cron startował 5–8 godzin po czasie, więc „nocny” przebieg czterech urządzeń zaczynał się około 08:30–09:00 i przeplatał z testami PR-ów (16.11 skończył o 11:53, po agencie dev z 10:00). Trzy dzienne przebiegi testowały kod, który się nie zmienił: main stał dwa dni na jednym commicie i przeszedł cały zestaw 6 razy.

Było Jest
Kto startuje cron GitHuba (schedule:) dwa timery systemd użytkownika na uwh → gh workflow run
Przebieg nocny (4 urządzenia, zapisuje issue) 01:17 UTC, w praktyce ~08:30 czasu polskiego 03:17 czasu polskiego, co noc
Przebiegi dzienne (Desktop Chrome) 3 razy na dobę, zawsze sprawdzenie o 09:17 / 15:17 / 21:17; przebieg rusza tylko, gdy zmienił się main albo schemat bazy dev
Agent dev (gate.sh) liczy przebiegi z schedule liczy przebiegi z timerów na main (stare schedule też, dla ciągłości)

„Zmieniło się” rozstrzyga klucz <8 znaków SHA main>-<8 znaków skrótu schematu dev>. Trafia do nazwy przebiegu (np. Nightly E2E · daytime · cd143ef9-db35c27f); następne sprawdzenie szuka go w ostatnich przebiegach. Na uwh nie powstaje żaden plik stanu. Ręczny przebieg jednego urządzenia działa jak dotąd (kind=manual, pole projects).

Jak sprawdzić ręcznie

  1. Decyzja bez startu (uwh, po scaleniu): 
    NIGHTLY_TRIGGER_DRY_RUN=1 ~/strummy-prod-e2e/checkout/scripts/ops/nightly-e2e/trigger.sh daytime
    Oczekiwane: dry run — would dispatch … (key: …), gdy stan nie ma jeszcze przebiegu, albo … already has a run — nothing changed, skipping.
  2. Timery: systemctl --user list-timers 'strummy-nightly-e2e*' — dwa wpisy, następny nocny o 03:17.
  3. Przebieg dzienny: systemctl --user start strummy-nightly-e2e@daytime.service, potem journalctl --user -u 'strummy-nightly-e2e@*' -n 5. W Actions pojawia się Nightly E2E · daytime · <klucz> z jednym urządzeniem; issue nightly-e2e zostaje nietknięte. Drugie uruchomienie zaraz potem: „skipping”.
  4. Rano po pierwszej nocy: przebieg Nightly E2E · nightly · … utworzony o 03:17 (01:17 lub 02:17 UTC), cztery urządzenia, issue zaktualizowane; w ~/strummy-dev-agent/history.log wpis agenta z 10:00 odnosi się do tego przebiegu.
  5. Przypadki brzegowe: kind=nightly z wypełnionym projects → przebieg pada w „Select projects” z komunikatem; zatrzymana baza dev → sprawdzenie dzienne kończy się błędem jednostki (bez przebiegu), nocny startuje bez klucza.

Po scaleniu

Jednostki są już skopiowane na uwh i włączone, ale nic nie robią, dopóki ~/strummy-prod-e2e/checkout nie dostanie skryptu z main (warunek ConditionPathExists; ten klon odświeża się co 4 godziny). Stare crony znikają razem ze scaleniem, więc przerwa trwa najwyżej do następnego cyklu audytu prod. Instalacja i wyłączenie: scripts/ops/nightly-e2e/README.md.
