Songs e2e locators + making main actually run e2e

2026-07-31 · branch fix/songs-list-e2e-locators

What was done

Two related problems. Both are about the E2E suite telling the truth.

1. Two e2e tests were failing deterministically — stale locators, not a broken feature

teacher/songs-crud.spec.ts and teacher-full-journey.spec.ts failed on every run where e2e actually executed — 15:14, 15:31, 16:47 on unrelated feature branches, and again on 2026-07-31 evening. Same tests, same lines, six hours apart. Deterministic, not flake.

Cause: commit a52a29ee (#615) changed a songs-list row from a link wrapping its content to a stretched empty link: 

// components/songs/SongsList.Row.tsx
<Link href={`/dashboard/songs/${song.id}`} aria-label={title} style={stretchedLinkStyle} />

The anchor now has no text content — the visible title sits in a sibling cell with pointerEvents: 'none'. So a:has-text("<title>") matches nothing. Song CRUD works perfectly; the test simply could not see it.

Fixed by matching the accessible name (which aria-label supplies):

- page.locator(`a:has-text("${TEST_SONG_EDITED}")`).first()
+ page.getByRole('link', { name: TEST_SONG_EDITED }).first()
One of these assertions was vacuous, not just failing The post-delete check expect(page.locator('a:has-text(…)')).toHaveCount(0) matched nothing whether or not the delete worked — it passed for the wrong reason. It is now a real assertion.

Lessons and assignments rows still wrap their text in the <Link>, so their locators were left alone. Only songs moved to the stretched-link pattern.

2. main reported the E2E workflow green while running no E2E tests

e2e.yml triggers on push: branches: [main, production]. But the e2e job's condition allowed only workflow_dispatch, the e2e label, or detect.outputs.risky — and detect runs only for pull_request. On a push to main all three are false, so the job skipped every time.

Observed on main's most recent "successful" run:

rls          success
types-drift  success
detect       skipped
e2e          skipped     <- never ran
db-parity    skipped

Fixed by adding github.event_name == 'push' to that condition.

Why this mattered The two broken tests above went unnoticed for days precisely because of this. E2E only ran on PRs touching risky paths; the branch that deploys to production never ran it at all, and reported green.

Cost of the workflow change

Cost Impact
Billed GitHub Actions minutes Zero. This job runs on the self-hosted EliteDesk runner (runs-on: [self-hosted, e2e]). The $200 incident that shaped this repo's CI discipline was about hosted runners and broad triggers; neither applies here.
Self-hosted runner time ~6 min per merge to main.
Queueing The runner is serial, so PR suites queue behind a main run. This is the actual trade: the branch that deploys to production gets a queue slot.
Concurrency safety Unchanged — group: e2e-${{ pull_request.number || github.ref }} is per-ref, so a main push cannot evict a running PR suite.

db-parity has the same dead-on-push condition and was deliberately not changed — it compares production against development, and those legitimately diverge between a migration landing on dev and the production cutover. Making it run on main would report red for a reason that is not a defect.

How to test it manually

Prerequisites

  • On the Orange LAN (dev Supabase is LAN-only)
  • .env.local pointing at StudentDevelopment
  • Playwright starts its own dev server — nothing to launch by hand

1. Run the two specs

npx playwright test tests/e2e/teacher/songs-crud.spec.ts \
  --project="Desktop Chrome" -g "song CRUD lifecycle" --reporter=line

npx playwright test tests/e2e/teacher-full-journey.spec.ts \
  --project="Desktop Chrome" --reporter=line

Both should pass. Before this change, both failed at the song-search step.

2. Prove the old locator really was the cause

Temporarily revert one locator back to page.locator(`a:has-text("${TEST_SONG_EDITED}")`) and re-run — it fails with "element(s) not found" while the song is plainly visible in the UI. That is the whole bug in one step.

3. Confirm the row markup by hand

  1. npm run dev, sign in as teacher, go to /dashboard/songs
  2. Inspect a song row. The <a> is empty, absolutely positioned, and carries aria-label with the title
  3. The title text lives in a sibling element, not inside the anchor

4. Confirm the workflow change (after merge)

Push anything to main and check the E2E workflow run. The e2e job should now execute instead of showing skipped: 

gh run list --workflow=e2e.yml --branch=main --limit 1
gh run view <id> --json jobs -q '.jobs[] | "\(.name)  \(.conclusion)"'

Expect e2e success rather than e2e skipped.

Edge cases worth checking

  • Accessible-name matching is whole-string by default. If a song title is ever truncated or decorated in aria-label, getByRole(…, { name }) stops matching. It currently uses the raw title, so this holds — but it is the assumption the fix rests on.
  • Duplicate titles. Both call sites use .first(); the test titles carry a timestamp so collisions are not realistic.
  • Queue contention. After this lands, merging several PRs in quick succession will serialise e2e runs on the single runner. Expect slower feedback on PRs during a merge burst.

Left alone deliberately

  • db-parity's identical dead-on-push condition — see the reasoning above.
  • Other a:has-text(…) locators in the suite. They target buttons and CTAs whose text really is inside the anchor ("New Song", "Create Lesson"), so they are unaffected by the stretched-link change.
  • The pending_students teardown error visible in local runs (PGRST205, table absent). Pre-existing, unrelated, non-fatal — but it does mean cleanup reports an error on every run, which is its own small source of noise.
