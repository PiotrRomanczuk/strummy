Songs List Redesign — Manual Test Report

Date: 2026-08-07 · Branch: feature/songs-list-redesign · Author: Claude Code session

What was done

Implemented the Strummy - Song List.html design from the imported Claude Design project (src/data.jsx, src/primitives.jsx, src/song-list.jsx) onto the real /dashboard/songs page, adapted to the app's actual data model and server-driven filtering (the mockup's fully-client in-memory filtering doesn't scale to a 393+ song catalog, so pagination/sort/filter stay URL-driven and server-rendered as before).

  • Category (genre) tabs — a new tab strip above the table, sourced from real distinct category values in the catalog (not a fixed enum), with counts. New service query loadCategoryBreakdown in lib/services/songs-list-queries.ts.
  • Sortable column headers — Title / Author / Level / Key / Added are click-to-sort with direction toggle and an arrow indicator, extending the existing sort-pill infrastructure (SongsListSort union gained _asc/_desc pairs). Learning/Mastery columns are display-only (computed, not DB columns).
  • Richer row visuals — cover art or a deterministic gradient placeholder (AlbumThumb.tsx), category·year subtitle under the title, a learner count and mastery bar per row (one bulk query per page via getSongsLearnerSummaries, not one query per row), and an "added" date column.
  • Slide-in detail panel — replaces the row's old inline "expand chevron" (superseded, since the panel shows the same fields plus more). Clicking a row opens a panel via ?selected=<id> in the URL (server-rendered, not client state) showing cover, key/capo/tempo/length, level/category/strum tags, usage stats and the currently-learning list (both reused from SongSidebar.tsx's existing UsageCard/LearnersCard), and a student-only "Want to learn" control. An explicit "Open full page" link still reaches the full SongDetail page.

Design decision: URL-driven panel, not client state

The mockup's row click sets local React state. Real implementation instead sets ?selected= in the URL and re-renders the panel server-side — consistent with how filters/pagination already work in this app, keeps the panel bookmarkable/shareable, and works without JavaScript (progressive enhancement) since the row is a real <a>. Approved with the user before implementation.

Bug found and fixed during manual verification

found via screenshot review The gradient placeholder for songs without cover art rendered as a blank white box for some song ids. Root cause: gradientForSong() used a signed right-shift (hash >> 3) on a hash that can exceed 231, which produced a negative array index for roughly half of all possible ids, so the second gradient color came out undefined and the whole background CSS value was invalid. Fixed by using the unsigned right-shift operator (hash >>> 3) in components/songs/AlbumThumb.tsx. Verified via getComputedStyle in a throwaway Playwright script before/after.

Known pre-existing issue (not introduced by this change)

The "Pending Requests" chip renders the literal text Songs.pendingRequests instead of its label — visible in both screenshots above. This is an existing missing-i18n-key bug in SongsList.Filters.tsx (the Songs.pendingRequests key doesn't exist in messages/en.json) that predates this redesign; this PR did not touch that code path. Flagging it here rather than fixing it silently, since it's out of this change's scope.

Not implemented from the mockup (scoped out, with reasoning)

  • Per-row avatar stack — mockup shows up to 4 overlapping student avatars per row. The app has no per-song "top learners" bulk query and no student avatar/photo infra; building both was out of scope for this pass. Shipped a learner count instead (still from one bulk query per page).
  • "Assign to student" button — mockup's panel has this, but no such teacher-initiated assignment flow exists in the codebase (assignments are a separate lesson-plan feature, unrelated to songs). Not fabricated; teachers get "Open full page" + "Edit song" instead.
  • Sidebar/topbar chrome — the mockup is a self-contained page including its own sidebar and topbar. The real app already renders those in app/dashboard/layout.tsx; bringing in the mockup's copies would have duplicated navigation chrome.
