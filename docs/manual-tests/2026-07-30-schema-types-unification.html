Manual test — schema types unification

Date 2026-07-30  ·  Branch claude/project-maintenance-cleanup-c413ce  ·  Scope Phase 2 of the maintenance cleanup plan

What was actually done

The repo carried three separate copies of the generated Supabase schema types (database.types.ts at the root, types/database.types.ts, and types/database.types.generated.ts), each imported by different parts of the app and each stale in a different way. Parsing the public.Tables block of each gives 38, 36 and 35 tables — against a live schema with 62. All three also described three tables (lesson_history, song_sections, student_song_progress) that exist in neither database, as a table or a view.

They are now one file, types/database.types.ts, generated from the live development schema, with all 29 import sites repointed at it. Development and production were verified table-for-table identical first (62 each, zero difference in either direction), so generating from dev is safe.

The bug this was hiding

Unifying the types turned 18 latent runtime bugs into compile errors. The one that mattered:

profiles.email is nullable — shadow rows are created without one — but notification_log.recipient_email is NOT NULL. Every notification path wrote the former into the latter, and did so before the existing ADR-0002 deliverability chokepoint ran. A profile carrying no address would have failed the insert with a constraint violation. The stale types described email as string, so nothing could catch it.

Fixed by resolving email ?? invite_email once, up front, and returning a readable error if neither exists — before any log row is written.

This is behaviour-neutral on all existing data. All 3,811 profiles currently have an email (including all 34 shadow rows), so recordedEmail resolves to exactly the old value for every row that exists today. The new guard only covers the schema-permitted case that would previously have thrown. Nothing about who receives email changes.

Preventing recurrence

  • npm run db:types — regenerates the single file (scripts/database/gen-types.sh), piped through prettier so generation and the repo's format agree.
  • npm run db:types:check — regenerate and fail if it differs from git.
  • scripts/database/check-types-drift.sh — compares the committed types against the live schema, column by column. Wired into e2e.yml's existing self-hosted db-parity job, which is already gated on supabase/migrations changes. Not in ci.yml: that runs on ubuntu-latest, which cannot reach the LAN database.
  • types/database.types.ts added to the workflow's risky-path pattern, so hand-edits trip the check too.

Separately: lib/logging/ is gone

lib/ had three logging modules: logger.ts (the ADR-0003 facade, 307 imports), logger/ (its backends), and logging/. The third has been folded away — its index.ts barrel turned out to be dead (all 11 importers reached past it to the file directly), and notification-logger.ts moved to lib/notifications/, where its consumers live.

How to manually test it

Prerequisites: on the Orange LAN (the dev stack is at 192.168.1.75), repo on claude/project-maintenance-cleanup-c413ce, npm install done.

1 · The types match the live schema

bash scripts/database/check-types-drift.sh

types/database.types.ts matches the live schema (695 columns). and exit code 0.

2 · The drift gate actually fails (prove it is not blind)

Delete any one column line from a scratch copy and re-run against it:

cp types/database.types.ts /tmp/drift.ts
# remove one line such as `created_at: string;` from inside any Row block
TYPES_FILE=/tmp/drift.ts bash scripts/database/check-types-drift.sh; echo "exit=$?"

SCHEMA TYPES DRIFT: 1 column(s) missing…, the offending table.column named, and exit=1.

3 · Only one schema types file exists

git ls-files | grep database.types

Exactly one line: types/database.types.ts.

4 · Notifications still send normally (the behaviour-sensitive path)

This is the change worth eyeballing in the app. Sign in as the teacher account, then trigger a notification that goes to a normal profile — e.g. create or reschedule a lesson for a real student, or run npm run test:emails.

Delivery is unchanged. Then check the log row was written with the recipient's real address: 

psql -h 192.168.1.75 -p 55322 -U postgres -d postgres \
  -c "select notification_type, recipient_email, status, created_at
        from notification_log order by created_at desc limit 5;"

recipient_email is populated on every row — never blank.

5 · The new guard returns a clean error instead of crashing

The guard is unreachable with current data (every profile has an email), so this is optional and only worth doing if you want to see it fire. On dev only, null out one throwaway profile's address and attempt to notify it: 

-- dev stack only (port 55322), on a throwaway row
update profiles set email = null, invite_email = null where id = '<throwaway-id>';

sendNotification returns { success: false, error: 'Recipient has no email address' } and writes no notification_log row. Before this change the insert would have failed with a NOT NULL violation. Restore the address afterwards.

6 · Regeneration is reproducible

Requires Docker running locally (the supabase CLI shells out to it):

npm run db:types && git diff --stat -- types/database.types.ts

No diff — regenerating produces the committed file byte-for-byte. If Docker is not running, the header comment in scripts/database/gen-types.sh documents the pg-meta HTTP fallback, which is how this file was generated.

Known gaps

  • __tests__/history/lesson-history.unit.test.ts queries lesson_history — one of the three tables that does not exist. It passes because it is mock-backed and credential-gated, so it has never asserted anything about a real table and cannot fail. Left in place (deleting tests was out of scope for a types change); worth a decision.
  • The drift check compares table and column names, not TypeScript types. It catches a forgotten npm run db:types, which is the failure that actually happened — it would not catch a column whose type changed but whose name did not.
  • db-parity is gated on risky paths, so the drift check runs on migration and types-file PRs, not on every PR. Deliberate: the job is already scoped that way, and widening it would mean new workflow triggers.
