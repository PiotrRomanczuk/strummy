All four were deleted and rebuilt as asked.

How it was done

  1. Parsed each export for Ultimate Guitar links, using the message timestamp as the lesson date and de-duplicating per student on artist + title.
  2. Deleted the four existing accounts. The shared 451-song library was left untouched.
  3. Recreated each student through the app's own POST /api/users with the exact payload the “Add a student” form sends.
  4. Imported via the product's own CSV importer at /dashboard/users/<id>/import — which creates the songs, groups rows by date into lessons, links lesson_songs, and fills the repertoire. 0 errors across all four.
  5. Invited each student with “Invite to claim”. All four emails arrived in Gmail, and all four auth accounts exist and are linked to their profiles. They are not yet claimed — confirmed_at and last_sign_in_at are both null, because nobody has opened an invite link and set a password. The student-side view is therefore unverified.

Four bugs had to be fixed to get here

All four are the same underlying defect: an auth id used where a profiles.id is required. The two id spaces became independent in the July identity rebuild, so an auth id matches nothing.

What was broken Symptom PR
Teacher roster (GET /api/users) People page empty for every teacher, regardless of students #605
CSV song importer Every row failed: new row violates row-level security policy for table "lessons" #606
People page service Still empty after #605 — the page doesn't use that API; the API returned 4 while the page rendered 0 #607
Lesson edit & assignment edit Creating either failed the same RLS insert policy #607
The guard was widened twice. __tests__/architecture/profile-id-space.test.ts only matched the filter form (.eq('teacher_id', user.id)). It now also catches the insert form (teacher_id: user.id) and the alias form (an auth id assigned to something named teacherId/profileId) — the indirection blind spot the test documents in its own header. Recorded offenders went from 19 across 8 files to 32 across 17; the extra 13 were always broken, just invisible. The alias check found the lesson-edit and assignment-edit bugs immediately.

Why the existing tests never caught these: both edit-action test files reused a single constant for the caller's auth id and the expected teacher_id, so the assertion passed whichever id the code used. They now use distinct TEACHER_AUTH_ID and TEACHER_ID values. Worth applying to the rest of the sweep: a test that conflates the two ids is not testing this.

Still open

  • 18 known offenders remain in the ratchet baseline, across 8 files — the rest of the S2 identity sweep. Each is a feature that silently returns nothing for post-rebuild accounts.
  • Deleting a student silently does nothing. Two QA profiles “deleted” through the UI earlier were still present and active in the database hours later. Not investigated here.
  • These students belong to the test-teacher account (p.romanczuk+testteacher@gmail.com), not the owner account — that is the only teacher login available. If they should sit under the real owner, the lessons' teacher_id needs repointing.
  • A handful of titles lost punctuation in the URL slugs (What's Up, R.E.M., L'Olivier were restored by hand; others may still read plainly).
