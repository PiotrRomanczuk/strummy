deploy-db: each branch migrates its own database

Date: 2026-11-15 · Scope: .github/workflows/deploy-db.yml, the three schema checks in e2e.yml, migrate-db.sh, check-migrations-replay.sh, check-db-parity.sh, gen-types.sh, refresh.sh

What was done

Push to Database Applies Then checks
dev StrummyDevelopment pending files; destructive ones too, after a pg_dump (5 kept) — (PR checks cover dev; in-flight PRs may hold files there)
test StrummyTest pending files, under the refresh lock replay of test's migrations == StrummyTest
main StudentProduction pending files after a pg_dump; destructive ones wait for production-db replay of main's migrations == production → DB ready for production
  • The old main path migrated dev as a canary and then required prod == dev. With dev ahead of production by design, that compare could only go red. The canary is now StrummyTest (anonymised production), which gets every migration before main.
  • PR checks in e2e.yml (db-parity, migrations-replay, DB types drift) compare with the database of the branch the PR goes into: StrummyTest for a PR into main, dev otherwise. db-parity adds every migration the branch has and main does not (file tree, not history — squash merges are fine), not only the PR's own. They no longer run on a push to main: deploy-db's replay check covers it on every push and every 30 minutes.
  • refresh.sh and migrate-db.sh test share ~/strummy-test/.lock: a deploy never migrates a half-restored copy. The refresh also restores COMMENT ON SCHEMA public (the one line that differed from production).
  • All workflow steps run with shell: bash (pipefail): migrate-db.sh … | tee can no longer pass on a failed migration.

How to test after merge

Step Expected
Merge any PR into dev (or gh workflow run deploy-db.yml --ref dev) One job, Apply migrations (dev); the step summary says what was applied or Nothing pending on dev. No prod jobs, no "DB ready for production".
Merge dev → test Apply migrations (test), then StrummyTest == the test branch's migrations green — after StrummyTest was refreshed from the production backup (today it holds dev's #1005/#1027 objects and would be red).
Merge test → main Plan → Apply migrations → Production == main's migrations → DB ready for production green; Vercel aliases the build.
Open a PR into dev that adds a migration and apply it to the dev stack db-parity lists production's missing files (the PR's plus any waiting on dev) and goes green.
Start refresh.sh on uwh and push to test while it runs The deploy job waits for the refresh, then applies.

Known, not caused by this change

  • The dev stack holds migrations of two open, unmerged PRs (#1005, #1027), so every PR's schema checks are red until they merge or are reverted from dev.
  • Until this change reaches main, main's old deploy-db.yml (every 30 min) still compares prod with dev — it goes red as soon as the first migration lands on dev.
