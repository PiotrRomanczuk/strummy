Correction (measured during Phase 2). An earlier draft put these counts at 62 / 52 / 59. That grep conflated the Tables, Views and Functions blocks. Parsing the public.Tables block alone gives 38 / 36 / 35 — and the live schema has 62 base tables. So the situation was worse than the finding claimed: not three files disagreeing around a correct centre, but three files all badly behind a schema none of them matched, missing 13, 18 and 16 tables respectively.

Roughly a third of app/ therefore type-checks against a schema snapshot that predates the July identity rebuild, while the rest uses a different one. There is no supabase gen types script in package.json, which means all three are hand-maintained — precisely what CLAUDE.md forbids ("Never hand-edit types/database.types.ts as a substitute for a migration").

Add a codegen script, generate one file at types/database.types.ts, delete the other two, and repoint ~38 imports. Then wire it into CI so drift becomes a failing check rather than a discovery. 

"db:types": "supabase gen types typescript --db-url \"$SUPABASE_DB_URL\" > types/database.types.ts"
"db:types:check": "npm run db:types && git diff --exit-code types/database.types.ts"

Correction (verified during Phase 1). An earlier draft of this finding proposed adding an ESLint max-lines rule. It already exists — eslint.config.mjs:58 sets ['warn', { max: 200, skipBlankLines: true, skipComments: true }] over app/, components/ and lib/, with types/, supabase/ and all test globs exempted at line 73. max-lines-per-function (80) is configured alongside it. The proposal below is revised accordingly; the diagnosis is unchanged.

So the gate exists and is correctly configured. What's missing is consequence: npm run lint currently emits 297 warnings and 0 errors — 79 max-lines, 195 max-lines-per-function, 23 other. A warning count that only ever grows is indistinguishable from no rule at all. (The 53 figure above is raw wc -l over components/; ESLint's 79 is its blank/comment-adjusted count across all three directories. Both are correct for their scope — the lint number is the one that's actually enforced.)

Don't add the rule; add a ratchet. Record today's counts as a baseline and fail CI when either total increases — new violations get blocked, the existing 274 get fixed on touch rather than in a big-bang pass. The Parent.Section.tsx convention already in the style rules is the natural split mechanism; SongImportForm and SignUpForm are the obvious first candidates. 

# baseline, committed and compared in CI
npx eslint . -f json | jq '[.[].messages[] | select(.ruleId | test("max-lines"))] | length'

Proposed sequence

Ordered so that each phase leaves the tree in a shippable state, and so the cheap noise-reduction happens first — every later phase is easier to review against a quieter baseline.

Phase 1 Clear the deck

~1h · one chore/ PR · no source changes

Phase 2 Fix the correctness hazards

~3h · one fix/ PR · highest value in the document

Phase 3 Collapse the duplicate homes

~4h · one refactor/ PR · pure moves, imports mostly unchanged

Phase 4 Make the rules true

~2h · docs + lint config · no source moves

Phase 5 The v2 decision

1h or 1–2d, depending on the answer · blocked on your call

What this plan deliberately does not touch

  • Behaviour. Every proposal above is a move, a delete, or a config change. No runtime logic is modified, which is what makes Phases 1–3 reviewable as pure diffs.
  • The 44 live migrations. Untouched — only the 173-file archive is discussed.
  • The 178 Bruno request files and the mcp/strummy-server workspace. Both are self-contained, internally consistent, and carry their own READMEs. No action needed.
  • README.md (498 lines). Long for a README, but it's recruiter-facing portfolio surface, not developer documentation. Length is the point.
  • Test coverage. Out of scope here; this document is about where files live, not what they assert.

The one-line version

Nothing here is rot — it's the residue of four or five migrations that were 80% completed and then correctly deprioritised for shipping. Phase 2 is a real bug surface and should happen regardless. Phases 1 and 3 are two days of mechanical work that would remove roughly 40 files and every “which one of these is the real one?” decision from the daily loop.
